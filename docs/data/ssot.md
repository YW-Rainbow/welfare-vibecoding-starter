# 이용자 데이터를 단일 원본으로 관리하는 방법

> 출처·최신판: https://github.com/YW-Rainbow/welfare-vibecoding-starter
> `../assess/form-audit.md`가 무엇을 만들지 정하고 `../workflow.md`가 구현 플랫폼을 정한다면, 이 문서는 여러 앱과 파일이 어떤 데이터를 원본으로 사용할지 정합니다. 앱을 두 개 이상 만들 계획이라면 먼저 확인하세요.

## 중복 입력과 수작업 취합의 문제

종이 출석부의 내용을 시트에 입력하고 다시 실적표로 복사하면 단계마다 누락과 오입력이 생깁니다. 담당자마다 별도 파일을 사용하면 같은 이용자의 이름과 정보가 서로 다르게 기록되어 실인원을 계산할 때 사람이 직접 대조해야 합니다. 이 문제는 담당자의 주의력보다 같은 정보를 여러 곳에 입력하게 만든 구조에서 발생합니다.

목표는 취합을 더 빠르게 하는 것이 아니라 **같은 사실을 한 번만 입력하고 다른 기록이 그 원본을 참조하게 만드는 것**입니다. 이를 SSoT(Single Source of Truth, 단일 원본)라고 합니다.

## 두 가지 기본 규칙

1. **이용자는 이용자 명부에서만 등록합니다.** 개별 앱과 업무 시트에서 별도의 이용자 정보를 만들지 않습니다.
2. **모든 기록은 이용자 ID로 연결합니다.** 이름을 반복 입력하지 않고 이용자 명부의 고정된 ID를 참조합니다.

이 두 규칙을 지키지 않으면 앱이 늘어날수록 중복 데이터와 수작업 대조 비용도 함께 늘어납니다.

## 사회복지기관의 기준 데이터는 이용자입니다

일반적인 기업 시스템은 직원을 중심으로 데이터를 구성하기도 하지만 사회복지기관에서는 이용자를 기준으로 참여, 상담, 후원, 사례관리 기록을 연결해야 합니다. 그래야 이용자별 장기 변화와 재이용 현황을 확인하고 실적의 실인원을 정확하게 계산할 수 있습니다.

## 권장 데이터 구조

```
[기준 데이터]
이용자 명부       이용자 ID를 발급하는 유일한 원본
프로그램 목록     프로그램 ID, 사업 구분, 유형, 목표 인원
프로그램 회차     프로그램 ID + 회차 ID, 일시, 장소, 강사, 주제

[업무 기록]
사업·팀별 기록    참석한 이용자를 한 행씩 기록하고 이름·성별·일시는 반복 저장하지 않음

[집계]
총괄 실적         업무 기록을 자동으로 집계하고 마지막 단계에서 명부와 조인함
```

총괄 실적에는 담당자가 값을 직접 입력하지 않습니다. 업무 기록에서 자동으로 가져오고 집계해야 복사 과정에서 생기는 누락과 불일치를 방지할 수 있습니다.

## 참여 기록의 기본 컬럼

| 컬럼 | 의미 | 다른 테이블과 연결해 확인할 정보 |
|---|---|---|
| 기록 ID | 한 행의 고유 식별자 | 입력자, 입력 시각, 메모 |
| 프로그램 ID | 참여한 사업 | 사업 구분, 유형, 목표 인원 |
| 회차 ID | 프로그램의 특정 회차 | 일시, 장소, 강사, 주제 |
| 이용자 ID | 참여한 이용자 | 성별, 생년월일, 해당 연도의 연령 |
| 취소 여부 | 잘못 입력하거나 취소된 기록인지 표시 | 해당 없음 |

참여 기록에는 이름, 성별, 회차 일시를 반복해서 저장하지 않습니다. ID를 통해 필요한 정보만 조회하면 중복 수정과 표기 불일치를 줄이고 파일별 접근 범위도 나눌 수 있습니다.

연령대는 해마다 달라지므로 기록에 `60대`처럼 고정해서 저장하지 않습니다. 이용자 명부에는 생년월일을 저장하고 보고서의 기준 연도에 따라 연령대를 계산합니다. 성별처럼 이용자 기준 데이터도 명부에서 관리합니다.

### 결석과 취소를 구분합니다

일반적인 참여 실적은 참석한 사람만 한 행으로 기록합니다. 결석자까지 회차마다 생성하면 데이터 양이 늘고 실제 참여 건수를 계산할 때 매번 제외해야 합니다. 출석률이 필요한 프로그램만 별도의 등록자 명단과 참석 기록을 비교해 계산합니다.

취소는 결석과 다릅니다. 잘못 입력하거나 중복 입력한 행을 삭제하면 수치가 변경된 이유를 확인할 수 없습니다. 기존 행에 취소 여부와 취소 사유를 기록하고 집계에서는 취소되지 않은 행만 사용합니다. 증거로 사용하는 기록에는 `record-integrity.md`의 변경 이력 기준을 추가로 적용합니다.

### 행 번호를 ID로 사용하지 않습니다

Google Sheets의 행 번호는 행 삭제와 정렬에 따라 바뀌므로 식별자로 사용할 수 없습니다. 저장할 때 UUID 등 변경되지 않는 기록 ID를 생성합니다. 시트 수식으로 ID를 만들었다면 결과를 값으로 고정해야 행 이동이나 정렬 뒤에도 ID가 유지됩니다.

프로그램 ID와 회차 ID도 한 문자열로 합치지 않고 별도 컬럼으로 저장합니다. 예를 들어 `2026-어르신교실-03`을 한 칸에 저장하면 프로그램만 집계할 때 문자열을 다시 분리해야 하고 표기 오류에도 취약합니다. 두 컬럼으로 나누면 각각 유효성 검사를 적용하고 프로그램별 집계를 바로 수행할 수 있습니다.

## Google Sheets로 구현하는 경우

Google Sheets를 선택했다면 개인정보를 다른 플랫폼에 중복 저장하지 않고 가능한 범위에서 Google Workspace 안에 구성을 완료합니다. 플랫폼이 늘면 개인정보 처리 수탁자와 계정·백업·인수인계 범위도 늘어납니다. Google Sheets는 행 단위 권한을 제공하지 않으므로 접근 권한이 다른 데이터는 파일을 분리합니다.

```
① 이용자 명부       전 직원 조회 / 명부 담당자만 수정
② 참여·출결 기록    프로그램 담당자 수정
③ 사례관리 기록     담당자와 슈퍼바이저만 접근
④ 총괄 실적         ①과 ②를 자동 집계 / 직접 입력 금지
```

③ 사례관리 파일에서 ④ 총괄 실적으로는 상담 내용이 아니라 집계 결과만 전달합니다. 사례관리 파일 전체를 `IMPORTRANGE`로 가져오면 접근 권한을 파일별로 분리한 의미가 없어집니다. ③ 안에 별도의 집계 탭을 만들고 필요한 숫자 범위만 ④에서 가져옵니다.

```
③ 사례관리  ├─ 기록 탭: 상담 내용, 외부 파일로 전달하지 않음
             └─ 월별 집계 탭: 건수와 실인원 등 집계값만 제공
                                      ↓ IMPORTRANGE 범위를 월별 집계로 제한
④ 총괄 실적
```

이용자와 프로그램 컬럼은 데이터 유효성 검사를 사용해 명부에 있는 값만 선택하게 합니다. 각 업무 파일에 명부를 `IMPORTRANGE`로 불러오는 숨김 탭을 만들고 그 범위를 선택 목록으로 사용하면 이름의 띄어쓰기와 표기 차이로 실인원이 달라지는 문제를 줄일 수 있습니다.

조인은 원본 행 전체가 아니라 집계가 끝난 결과에 적용합니다. 수만 행에 `VLOOKUP`을 반복 적용하면 시트의 응답 속도가 느려집니다.

```
업무 시트 ──IMPORTRANGE──→ 원본 모음 탭
                                  ↓ QUERY로 먼저 집계
                              집계 탭
                                  ↓ 이용자 명부 조인
                              최종 실적표
```

실인원은 집계 전에 이용자 ID의 중복을 제거해야 하므로 별도의 실인원 집계 탭이나 `UNIQUE`·`QUERY` 조합을 사용합니다.

Google Sheets 구성에서는 다음 네 가지를 지킵니다.

1. 사례관리 파일은 링크 공유를 끄고 다운로드·복사·인쇄 권한도 필요한 범위로 제한합니다. 앱에서만 접근한다면 사람에게는 파일을 직접 공유하지 않습니다.
2. Google Sheets만으로는 필요한 접근 로그가 자동으로 생성되지 않을 수 있습니다. 앱에서 조회·수정·삭제·출력할 때 별도의 로그를 남기고 적용되는 보관 기간을 확인합니다.
3. `IMPORTRANGE`는 기준 데이터와 업무 기록에서 총괄 실적으로 이동하는 한 방향으로만 사용합니다. 총괄 실적의 값을 원본에 다시 쓰지 않습니다.
4. 총괄 실적에는 직접 입력하지 않습니다. 집계 결과가 잘못되었다면 기준 데이터나 업무 기록을 수정합니다.

## 기존 데이터 이관

기존 시트와 문서의 데이터를 새 명부와 연결할 때는 누락과 잘못된 이용자 연결을 방지하기 위해 다음 순서를 적용합니다.

1. **원본 보존**: 기존 파일을 삭제하거나 덮어쓰지 않고 읽기 전용으로 보관합니다.
2. **정규화**: 컬럼 이름, 날짜, 전화번호, 코드 등 값의 형식을 표준 구조에 맞춥니다.
3. **대응표 작성**: 기존 행의 식별 정보와 새 이용자 ID를 연결한 표를 남깁니다.

실제 이관 전에 백업, dry-run, 표본 대조, 관리자 승인을 수행합니다. dry-run은 새 원본에 쓰지 않고 변환 결과와 오류 목록만 만드는 시험 실행입니다. 장기간 쌓인 기록은 일부가 누락되어도 다시 만들기 어려우므로 기능 개발 속도보다 이관 데이터의 정확성과 복구 가능성을 우선합니다.

### 문제가 있는 행은 삭제하지 않고 품질 등급을 기록합니다

ID 누락, 중복, 잘못된 날짜처럼 문제가 있는 행을 이관 과정에서 자동 삭제하지 않습니다. 다음 품질 등급을 함께 저장하고 C와 D는 담당자가 확인합니다.

| 등급 | 기준 | 사용 방법 |
|---|---|---|
| A | 검증 결과 문제 없음 | 그대로 사용 |
| B | 표기 불일치 등 경미한 문제 | 사용 가능, 이후 정리 |
| C | 범위를 벗어난 값이나 날짜 오류 등 확인 필요 | 담당자 확인 후 사용 |
| D | ID 없음, 중복, 상호 모순 등 신뢰하기 어려움 | 공식 보고서와 분석에서 제외하되 원본은 보존 |

D등급 행을 보존하면 이후 원본과 다시 대조해 복구할 수 있고 데이터 품질 문제의 규모도 확인할 수 있습니다. 공식 집계에서는 제외 사유와 건수를 함께 기록합니다.

### 구조화된 값과 서술 기록을 함께 보존합니다

날짜, 횟수, 분류 같은 구조화된 컬럼은 집계에 필요하지만 그 수치가 나온 배경을 모두 설명하지는 못합니다. 기존 서술 기록을 삭제하지 말고 관련 행과 연결해 보존합니다. AI 분석을 도입하기 전에는 무엇을 어떤 기준으로 기록하는지 먼저 통일해야 합니다. 입력 기준이 제각각이면 AI가 만든 요약과 분류도 일관되게 검증할 수 없습니다.

## 담당자별 앱을 만드는 경우

담당자가 업무에 맞는 화면과 기능을 따로 만드는 것은 가능합니다. 그러나 앱마다 이용자 명부와 별도 데이터베이스를 만들면 같은 사람이 서로 다른 ID로 등록되고, 담당자 퇴사 후 관리되지 않는 개인정보 저장소가 남을 수 있습니다.

공용 기준 데이터와 담당자 전용 데이터를 다음과 같이 분리합니다.

| 구분 | 데이터 | 저장 원칙 |
|---|---|---|
| 공용 원본 | 이용자 명부, 참여 기록, 프로그램·회차 목록 | 모든 앱이 같은 원본을 참조 |
| 담당자 전용 | 사례 메모, 개인 태그, 진행 단계, 다음 방문 예정 | 별도 테이블이나 시트에 저장하되 이용자 ID로 연결하고 담당자에게만 접근 허용 |

담당자는 화면과 전용 항목을 업무에 맞게 구성할 수 있지만 이용자는 새로 등록하지 않고 공용 명부에서 선택합니다. 이 구조는 담당자의 업무 자율성을 유지하면서도 기관의 실적 집계와 인수인계를 가능하게 합니다.

## API와 MCP 접근 권한

여러 앱이 하나의 원본을 사용하면 일관성을 높일 수 있지만 공용 원본의 권한을 잘못 설정했을 때 영향을 받는 범위도 커집니다.

- 앱마다 필요한 테이블과 행만 허용합니다. RLS는 deny-by-default로 설정하고 모든 직원에게 전체 데이터 접근 권한을 주지 않습니다.
- MCP는 개인정보가 없는 집계 뷰를 기본으로 연결합니다. MCP가 이용자 데이터베이스를 직접 조회하면 실제 개인정보가 AI 서비스로 전송될 수 있습니다. 개인별 상담 이력을 제공하기 전에 `../requirements/masking.md`의 계약·동의·처리방침 조건을 확인합니다.
- 쓰기 API는 서버에서 입력값과 사용자 권한을 검증하고 변경 이력을 기록합니다. 앱이 임의로 기준 데이터의 컬럼이나 ID를 만들지 못하게 합니다.

## 도입 범위

처음부터 기관의 모든 시스템을 통합할 필요는 없습니다. 이용자 명부 하나를 원본으로 정하고 다음에 만드는 앱이 그 명부의 이용자 ID를 참조하게 하는 것부터 시작합니다. 이후 프로그램 목록과 회차 목록처럼 여러 업무가 공통으로 사용하는 데이터를 단계적으로 추가합니다.

단일 원본은 모든 데이터를 한 파일에 저장한다는 뜻이 아닙니다. 접근 권한에 따라 파일과 테이블을 나누더라도 모든 앱이 같은 ID 체계와 기준 데이터를 사용하면 됩니다.

이 문서는 `levels.md`의 2단계에 해당합니다. 앱이 세 개를 넘고 스키마와 접근 권한을 관리할 담당자가 있다면 공용 데이터 레이어와 API를 운영하는 3단계를 검토합니다. 관계와 기관의 판단 기준까지 데이터로 관리할 필요가 있다면 4단계를 검토합니다. 현재 문제가 명부 중복에 한정된다면 2단계를 유지하는 것으로 충분합니다.
