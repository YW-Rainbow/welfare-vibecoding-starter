# 당사자용 화면 설계 기준

> 출처·최신판: https://github.com/YW-Rainbow/welfare-vibecoding-starter
> `../workflow.md` 원칙 6이 화면 문구를 다룬다면, 이 문서는 UI와 웹 접근성 구현 기준을 다룹니다. `../assess/ethics.md`의 적정기술 원칙을 화면에 적용하기 위한 문서입니다.
> 당사자가 직접 사용하는 화면을 설계할 때 적용합니다. 법령 인용은 2026년 8월 기준이며, 이 문서는 법률 자문이 아닙니다.

## 적용 기준

데이터 등급(S/P/N)은 개인정보의 민감도를 나타내고, 보관 등급은 기록의 증거성을 나타냅니다. 이 문서는 별도의 기준으로 **누가 화면을 사용하는지** 확인합니다.

개인정보가 없는 N등급 안내 페이지라도 어르신이나 장애인이 직접 사용한다면 이 문서의 접근성 기준을 적용해야 합니다. 법적 근거는 장애인차별금지법 제21조의 정보통신·의사소통에서의 정당한 편의 제공이며, 구현 기준은 한국형 웹 콘텐츠 접근성 지침(KWCAG)을 참고합니다.

접근성은 UI를 완성한 뒤 추가하지 않습니다. 색상, 레이아웃, 입력 구조를 정하기 전에 글자 크기, 색 대비, 키보드 조작, 스크린 리더 지원 방식을 함께 설계해야 재작업을 줄일 수 있습니다.

## 화면을 설계하기 전에 사용자 환경을 작성합니다

화면을 그리기 전에 다음 문장을 먼저 작성합니다.

> 이 화면은 [사용자]가 [사용 장소]에서 [사용 기기]로 사용합니다.

예: “이 화면은 75세 이상 어르신이 경로당에서 본인 휴대폰으로 사용합니다.”

사용자, 장소, 기기를 정하지 못했다면 글자 크기와 터치 영역, 네트워크 조건을 결정할 수 없습니다. 먼저 실제 사용 환경을 확인하세요.

## 사용자별 주요 설계 기준

| 사용자 | 적용할 설계 기준 |
|---|---|
| **어르신** | 글자와 버튼을 크게 만들고 한 화면에 주요 작업 하나만 배치합니다. 선택지를 줄이고, 잘못 누른 동작을 되돌릴 수 있게 하며, 짧은 시간 제한을 두지 않습니다. |
| **저시력·시각장애인** | 스크린 리더가 내용을 읽을 수 있게 시맨틱 HTML을 사용합니다. 정보를 색으로만 구분하지 않고, 200% 확대에서도 내용이 잘리거나 겹치지 않게 만듭니다. |
| **발달장애인·저문해력 당사자** | 한 문장에 한 가지 정보만 넣고 쉬운 단어를 사용합니다. 필요한 경우 그림을 함께 제공하고 색·소리·움직임 같은 자극을 줄입니다. 화면 문구는 EASYREAD로 검토합니다. |
| **손 떨림·마비가 있는 사용자** | 터치 영역을 크게 만들고 버튼 사이의 간격을 확보합니다. 삭제나 제출처럼 위험한 동작은 자주 누르는 버튼과 떨어뜨립니다. |
| **청각장애인** | 알림을 소리로만 제공하지 않고 화면에도 표시합니다. 영상에는 자막을 제공합니다. |
| **직원** | 반복 입력 속도를 우선하되 기본 글자 크기, 색 대비, 키보드 조작 기준은 동일하게 적용합니다. |

## 기본 수치

다음 값은 바이브코딩을 시작할 때 AI에게 그대로 전달할 수 있는 기본값입니다.

| 항목 | 일반 화면 | 당사자용 화면 |
|---|---|---|
| 본문 글자 크기 | 16px 이상 | 18~20px |
| 버튼 글자 크기 | 16px 이상 | 20px 이상 |
| 터치·클릭 영역 | 44×44px 이상 | 56×56px 이상, 요소 사이 간격 8px 이상 |
| 글자와 배경의 명암비 | 4.5:1 이상 | 7:1 이상 |
| 큰 글씨·아이콘의 명암비 | 3:1 이상 | 4.5:1 이상 |
| 한 화면의 주요 동작 | 3개 이하 | 1개 |
| 한 문장 길이 | 별도 제한 없음 | 40자 이하 권장 |
| 자동 로그아웃 | 보안 기준에 따라 설정 | 만료 전에 안내하고 연장할 수 있게 설정 |

CSS에서는 가능하면 글자 크기를 `px`로 고정하지 않고 `rem`을 사용합니다. 사용자가 브라우저나 휴대폰의 기본 글자 크기를 키웠을 때 화면의 글자도 함께 커져야 합니다.

## 화면 문구 작성 기준

접근 가능한 레이아웃을 만들었더라도 버튼 이름과 오류 메시지가 어렵다면 사용자는 기능을 완료할 수 없습니다. 화면 문구에는 다음 기준을 적용합니다.

| 항목 | 기준 |
|---|---|
| **문장** | 한 문장에는 한 가지 정보만 넣고, 버튼 하나에는 한 가지 동작만 연결합니다. |
| **어휘** | “인증”, “승인 대기”, “반려” 같은 행정·기술 용어는 사용자가 이해할 수 있는 표현으로 설명합니다. |
| **날짜와 숫자** | “익일”, “3영업일 이내” 대신 실제 날짜를 표시합니다. |
| **구성** | 여러 항목은 긴 문장보다 목록으로 제시하고 한 화면에는 한 주제만 배치합니다. |
| **표기** | `~`는 “부터/까지”, `/`는 “또는”처럼 의미가 분명한 말로 바꿉니다. |
| **정확성** | 문장을 쉽게 바꾸더라도 날짜, 금액, 기관명, 연락처 같은 필수 정보는 생략하지 않습니다. |

예를 들어 “신청 마감 2026년 9월 30일 오후 6시”를 “9/30 마감”으로 줄이면 종료 시각이 사라집니다. 화면 공간이 부족하면 글자와 정보를 줄이지 말고 화면을 여러 단계로 나누세요.

## 배포 전 필수 체크리스트

`../../rules/agentic.md`의 배포 게이트에 다음 항목을 추가합니다.

- [ ] Tab 키만으로 모든 기능을 사용할 수 있다.
- [ ] 현재 포커스가 있는 요소가 화면에 표시된다. `outline: none`을 사용했다면 대체 포커스 스타일이 있다.
- [ ] 정보가 있는 모든 이미지에 적절한 대체 텍스트가 있다. 장식용 이미지는 `alt=""`를 사용한다.
- [ ] 모든 입력 필드에 연결된 `label`이 있다. `placeholder`를 label 대신 사용하지 않는다.
- [ ] 오류와 상태를 색으로만 표시하지 않고 텍스트나 아이콘을 함께 제공한다.
- [ ] 브라우저를 200%로 확대해도 글자와 컨트롤이 잘리거나 겹치지 않는다.
- [ ] 휴대폰을 가로와 세로로 회전해도 주요 기능을 사용할 수 있다.
- [ ] 제목 요소가 `h1 → h2 → h3` 순서로 구성되어 있다.
- [ ] 동작은 `<button>`, 페이지 이동은 `<a>`를 사용한다. 클릭 이벤트를 연결한 `div`로 대신하지 않는다.

키보드 조작, 포커스 표시, 대체 텍스트, label, 색상 외 정보 제공은 하나라도 충족하지 못하면 배포하지 않습니다. 나머지 항목은 앱의 사용 환경에 따라 판단할 수 있지만, 제외한 항목과 이유를 기록해야 합니다.

## 실제 사용자 테스트

자동 검사와 체크리스트는 속성이 존재하는지만 확인할 수 있습니다. 예를 들어 `alt="이미지"`는 형식 검사를 통과할 수 있지만 사용자에게 필요한 정보를 제공하지 않습니다. 따라서 배포 전에 실제 사용자 테스트를 진행해야 합니다.

- 당사자에게 별도의 설명 없이 화면을 사용해 달라고 요청하고, 작업을 완료하지 못하거나 멈추는 지점을 기록합니다.
- 어르신용 화면은 해당 연령대의 어르신에게 직접 확인합니다. 앱을 만든 직원만 테스트해서는 사용자의 어려움을 찾기 어렵습니다.
- 발달장애인과 저문해력 당사자가 읽는 문구는 당사자 감수를 거쳐 확정합니다. EASYREAD가 만든 결과도 감수 전 초안으로 취급합니다.

테스트 중에는 옆에서 사용법을 알려 주지 않습니다. 도움이 필요했던 지점 자체가 UI에서 수정해야 할 항목입니다.

## 개인별 화면을 만드는 경우

발달장애 당사자는 감각 특성, 의사소통 방식, 정보 이해 방식이 서로 다를 수 있습니다. 한 사용자에게 도움이 되는 소리나 애니메이션이 다른 사용자에게는 과도한 자극이 될 수 있으므로, 범용 화면 하나가 모든 사람에게 적합하다고 가정하지 않습니다.

바이브코딩을 이용하면 같은 데이터와 기능을 사용하면서도 개인별 UI를 비교적 적은 비용으로 만들 수 있습니다. 개인별 화면을 만들 때는 다음 순서를 따릅니다.

1. 관찰과 기존 기록을 검토해 당사자에게 필요한 지원을 정의합니다.
2. 핵심 기능만 구현한 화면을 현장에서 사용합니다.
3. 당사자의 반응과 사용 결과를 기록합니다.
4. 기록을 바탕으로 화면을 유지, 수정, 중단할지 결정합니다.

당사자가 사용을 거부하거나 흥미를 잃었다면 사용을 설득하기보다 화면이나 지원 방식을 다시 검토합니다. 목적은 앱 사용률을 높이는 것이 아니라 당사자가 활동과 서비스를 이용할 수 있도록 환경을 조정하는 것입니다.

## 자주 발생하는 UI 문제

- **아이콘만 있는 버튼**: 톱니바퀴 아이콘만으로 “설정”을 표현하지 말고 아이콘 옆에 텍스트를 표시합니다.
- **대비가 낮은 회색 글자**: 디자인 시스템의 색상 토큰 단계에서 명암비를 확인합니다.
- **자동 재생 배너**: 읽기 전에 내용이 바뀔 수 있으므로 자동 전환을 끄거나 사용자가 직접 넘기게 합니다.
- **중첩 모달**: 포커스 이동과 닫기 동작이 복잡해집니다. 당사자용 화면에서는 모달을 최소화하고 한 화면 안에서 작업을 완료하게 합니다.
- **한 화면에 긴 입력 폼 배치**: 입력 항목을 여러 단계로 나누고 현재 단계와 남은 단계를 표시합니다.
- **되돌릴 수 없는 동작**: 삭제와 최종 제출 전에 확인하고, 가능한 경우 실행 뒤에도 일정 시간 취소할 수 있게 합니다.

## 디지털 외 이용 방법

화면 접근성을 충족해도 스마트폰이나 웹을 사용할 수 없는 사람이 있습니다. 다음 대체 방법을 함께 운영합니다.

- 종이, 전화, 대면 신청 방법을 제공합니다.
- 담당자가 대신 입력할 수 있게 하고 대리 입력 여부를 기록합니다.
- 링크를 보내기 전에 당사자가 해당 기기에서 링크를 열고 사용할 수 있는지 확인합니다.

## AI에게 전달할 UI 요구사항

코딩을 시작할 때 다음 내용을 프롬프트나 요구사항에 포함합니다.

```
이 화면은 [사용자]가 [사용 장소]에서 [사용 기기]로 사용합니다.
- 본문 18px 이상, 버튼 글자 20px 이상, CSS 크기는 rem 사용
- 터치 영역 56×56px 이상, 요소 사이 간격 8px 이상
- 글자와 배경 명암비 7:1 이상
- 한 화면에 주요 동작 하나
- 동작은 <button>, 이동은 <a> 사용. 클릭 이벤트를 연결한 div로 대체하지 않기
- 모든 입력 필드에 label 연결. placeholder를 label 대신 사용하지 않기
- 오류는 색과 텍스트로 함께 표시
- 정보가 있는 모든 이미지에 alt 제공, 장식용 이미지는 alt=""
- 키보드만으로 모든 기능 조작 가능, 포커스 표시 유지
- 자동 재생 배너와 짧은 시간 제한 사용 금지
- 버튼 이름과 오류 메시지는 사용자가 이해할 수 있는 말로 작성
- 날짜·금액·기관명·연락처는 생략하지 않기
```

## 이 문서를 적용하는 시점

- `../workflow.md` 문진 12번에서 당사자가 화면을 직접 사용한다고 확인했을 때
- 와이어프레임과 디자인 시스템을 만들기 전
- 기능 구현과 배포 전 접근성 테스트를 할 때
- 버튼 이름, 오류 메시지, 안내문을 작성할 때
- 실제 당사자와 사용자 테스트를 진행할 때

당사자용 문구는 EASYREAD로 검토하고, 기관 내부의 계획서와 보고서는 `urimal-for-socialworker`를 사용할 수 있습니다.
