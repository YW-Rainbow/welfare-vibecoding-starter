# 사례기록을 AI API로 전송할 때의 개인정보 및 마스킹 설계

> 출처·최신판: https://github.com/YW-Rainbow/welfare-vibecoding-starter
> 이 문서는 상담·사례관리 앱이 사례기록을 AI API로 전송하고 요약이나 개입 방향의 초안을 받는 기능을 다룹니다. 담당자가 기록을 일반 채팅창에 직접 붙여 넣는 경우는 대상이 아닙니다.
> **마스킹은 의무가 아니라 선택 사항입니다.** 지자체 협약, 업체 계약, 동의서, 개인정보 처리방침, 앱 동작이 요구사항을 충족하면 민감정보를 마스킹하지 않고 전송할 수 있습니다. 마스킹은 재식별 위험을 낮추기 위해 추가로 적용할 수 있는 보호 조치입니다.
> 마스킹 코드보다 아래의 사전 조건을 먼저 확인합니다. 마스킹해도 법적 동의가 면제되지 않으며, 마스킹해야만 AI API를 사용할 수 있는 것도 아닙니다.
> 계약·법령·가격은 2026-09-08에 원문을 확인했습니다("이 문서가 직접 확인한 것").
> 법률 자문이 아니며, 실제 도입 전 개인정보 전문가 검토를 거칩니다.

## 마스킹하지 않고 전송하기 위한 사전 조건

상담 앱이 원문을 AI API로 전송하려면 지자체 협약, 업체 DPA, 민감정보 동의, 국외 이전 근거, 앱의 서버 검증을 확인해야 합니다. 마스킹 구현 여부와 별개로 개발 전에 다음 순서로 검토합니다.

**0. 지자체 위수탁 협약서를 먼저 확인합니다.** 협약에 개인정보 반출이나 클라우드 이용을 제한하는 조항이 있다면 다른 조건을 충족하더라도 데이터를 전송할 수 없습니다. 이용자에 대한 개인정보 보호 의무와 지자체와 체결한 계약상 의무는 별도로 적용됩니다. 사회보장정보시스템(행복e음)에서 받은 자료는 반출 제한이 있을 수 있으므로 이 기능의 대상에서 제외하고, 기관이 직접 수집한 상담 기록만 검토합니다.

**1. AI 제공 업체의 DPA에서 민감정보 처리를 허용하는지 확인합니다.** 앱은 채팅 제품이 아니라 API를 사용하며, API 계정에는 업체의 데이터 처리 계약(DPA)이 적용됩니다. 다음 표는 각 업체의 계약 원문을 기준으로 민감정보 처리, 학습 사용, 보존기간을 비교한 결과입니다.

| API 서비스 | 민감정보 관련 계약 | 모델 학습 사용 | 보존기간 | 검토 결과 |
|---|---|---|---|---|
| **Anthropic API** | DPA(2025-02-24)와 이용약관에 민감정보·건강정보의 명시적 금지 조항이 없음. Schedule 1의 `특별범주: None`은 고객이 작성하는 설명 항목 | 미사용 | 기본 30일. Zero Data Retention(ZDR)은 별도 협의 | 계약 원문과 기관의 처리 조건을 확인해 사용. 미국 의료정보용 BAA는 별도로 신청 가능 |
| **Google Vertex AI / Gemini API 유료** | Cloud DPA가 고객 개인정보에 특별범주·민감정보를 포함한다고 정의. Gemini API 약관(2026-04-28)은 유료 서비스에 DPA를 적용 | 미사용(유료 서비스) | 서비스 정책에 따름 | 계약에 민감정보 관련 정의가 명시되어 있음. 무료 서비스는 학습과 사람의 검토에 사용될 수 있으므로 개인정보 전송 금지 |
| **OpenAI API** | DPA(v.010126) 제5조에 고객이 민감정보 전송을 의도하지 않는다는 취지의 문구가 있음. 일정 조건에서 API용 BAA 제공 | 미사용 | 기본 30일 | 표준 DPA만으로 기관의 민감정보 처리를 충족하는지 추가 검토하고 필요한 경우 BAA와 ZDR 조건 확인 |

세 회사의 비영리 할인은 사용자가 채팅 화면을 이용하는 좌석 요금제에만 적용되며 API 요금에는 적용되지 않습니다. 앱에서 사용하는 API는 실제 입력·출력 토큰 사용량을 기준으로 과금됩니다.

| 예: 상담 기록 하루 500건, 건당 약 1,000자 입력·요약 출력 | 하루 | 한 달 |
|---|---|---|
| Claude Haiku 4.5 ($1 / $5 per MTok) | 약 $2 | 약 $50 |
| Claude Sonnet 5 ($2 / $10 per MTok) | 약 $3.5 | 약 $105 |
| 같은 일을 Batch API로(50% 할인, 밤에 몰아서) | 절반 | 절반 |

**2. 개인정보보호법 제23조에 따른 민감정보 별도 동의를 확인합니다.** 건강, 장애, 정신건강, 학대 이력은 민감정보에 해당하므로 별도 동의가 필요합니다.

`../../ops/consent-form-sample.md`의 ④ 항목을 초기 상담 동의서에 포함할 수 있습니다. 이 동의는 마스킹 여부와 관계없이 필요합니다. 만 14세 미만 아동의 정보는 법정대리인의 동의를 별도로 받아야 합니다.

**3. 개인정보보호법 제28조의8에 따른 국외 이전 근거를 확인합니다.** 해외 AI API로 개인정보를 전송하면 국외 처리위탁에 해당합니다. 다음 두 가지 방식 가운데 적용 가능한 근거를 확인합니다.
- **제1항 제1호 별도 동의**: `../../ops/consent-form-sample.md`의 ③ 항목으로 동의를 받습니다. 이 저장소는 상담 기록을 AI로 분석할 때 별도 동의를 권장합니다.
- **제1항 제3호 개인정보 처리방침 공개**: 계약 이행에 필요한 처리위탁이라면 이전 항목, 국가, 시기와 방법, 이전받는 자, 목적과 보유기간, 거부 방법을 처리방침에 공개하는 방식으로 동의를 대체할 수 있습니다. AI 분석이 계약 이행에 반드시 필요한지 해석이 달라질 수 있으므로 이 방식만 적용하지 않고 별도 동의도 함께 검토합니다.

동의서에는 국외 이전 동의(③)와 민감정보 처리 동의(④)를 구분해 표시하고 개인정보 처리방침에도 AI 제공 업체와 처리 내용을 공개합니다. 개인정보보호법 제22조 제5항에 따라 이용자가 선택 동의를 거부했다는 이유로 서비스를 거부해서는 안 됩니다. 미동의 이용자의 기록은 담당자가 직접 정리하는 대체 절차를 제공해야 합니다(`../assess/ethics.md` 2번).

**4. 앱의 실제 동작이 동의서와 개인정보 처리방침에 일치하는지 확인합니다.** 이 단계에서 먼저 구현할 것은 마스킹 코드가 아니라 동의 상태를 서버에서 검증하고 전송·보관 정책을 지키는 코드입니다.

- 이용자 명부에 `동의_AI분석`, `동의_민감정보` 필드를 둡니다(`../data/ssot.md`). 두 값이 모두 참인 기록만 전송합니다. 클라이언트에서 버튼만 숨기지 말고 **서버에서 동의 상태를 검증**합니다.
- 미동의 이용자의 화면에는 AI 분석 기능을 표시하지 않고 담당자가 직접 작성하는 기능만 제공합니다.
- **AI 분석 결과만 저장하고 전송용 원문을 중복 저장하지 않습니다.** 원문은 기존 사례기록에 보관되어 있습니다.
- API 키는 서버(GAS 스크립트 속성, Worker 비밀 변수)에만 둡니다. 화면 코드에 넣지 않습니다.
- 누가 언제 어느 기록을 보냈는지 호출 기록을 남기고 2년 보관합니다(requirements.md 요건 8).
- 동의서의 "학습에 사용하지 않음"과 "즉시 파기" 문구가 실제 API 정책과 일치해야 합니다. 기관이 만든 전송용 원문을 즉시 삭제하더라도 AI 제공 업체가 API 요청을 기본 30일 보관한다면 두 보존기간을 구분해 고지합니다(`../../ops/consent-notes.md` 3·4).
- **마스킹하지 않는 앱에서는 동의서의 "직접 식별정보를 제거하고 전송합니다"라는 문구를 삭제합니다.** 실제 동작과 다른 설명을 동의서에 남기면 안 됩니다.
- AI에는 요약, 초안, 검토 후보 제시까지만 맡기고 급여나 서비스 자격을 자동으로 결정하게 하지 않습니다. 인공지능기본법상 고영향 AI와 자동화된 결정에 해당하는지 검토하고 허용 범위를 `DECISION.md`에 기록합니다.

위 조건을 모두 충족하면 **마스킹하지 않은 데이터를 전송할 수 있습니다.** 다음 절부터는 기관이 재식별 위험을 더 낮추기 위해 선택할 수 있는 마스킹 방법을 설명합니다.

## 마스킹을 추가로 적용할 조건

마스킹은 다음 조건에서 재식별 위험을 낮추거나 기관의 보호 조치를 입증하는 데 도움이 됩니다.

- **기관의 관할 지역이 작을 때**: 읍면 단위에서는 이름을 삭제해도 나이, 가족 형태, 장애 유형을 조합해 개인을 알아볼 수 있습니다. 이 경우 직접 식별정보 제거와 일반화를 함께 적용합니다.
- **동의를 받지 못한 기록을 통계나 경향으로만 분석할 때**: 기관이 재식별할 수 있는 매핑 테이블을 보관한다면 여전히 개인정보이므로 마스킹만으로 동의가 면제되지는 않습니다.
- **지자체 담당자에게 보호 조치를 설명해야 할 때**: 마스킹 정책, 탐지 로그, 표본 검수 결과를 안전조치의 근거로 제시할 수 있습니다.
- **사례기록 서식을 새로 설계할 때**: 실명 대신 역할 태그를 사용하면 사후 마스킹 비용을 줄이고 가족 관계에 대한 AI 분석 품질을 유지할 수 있습니다.

## 사례기록의 추가 식별 위험

사례기록은 등장인물과 기관이 많고 지역 범위가 작아 직접 식별정보를 삭제한 뒤에도 개인을 추정할 가능성이 높습니다.

- **등장인물이 많습니다.** 대상자뿐 아니라 가구원, 이웃, 유관기관 담당자의 이름과 관계가 함께 기록될 수 있습니다.
- **기관명이 많이 포함됩니다.** 행정복지센터, 정신건강복지센터, 병원, 학교 같은 기관명은 지역 정보와 결합될 때 개인을 추정하는 단서가 됩니다.
- **관할 지역이 작습니다.** 읍·면 단위에서는 `40대 한부모, 지체장애, 자녀 둘` 같은 준식별자 조합만으로도 특정 이용자를 추정할 수 있습니다.

## 마스킹 설계 원칙

### 1. 직접 식별정보와 분석에 필요한 민감정보를 구분합니다

> "40대 여성, 주요우울장애 진단, 3개월째 약물 중단, 야간 각성 호소"

위 문장에는 건강과 심리 상태에 관한 민감한 내용이 있지만 이름, 주소 등 개인을 직접 식별하는 정보는 없습니다. 다만 관할 지역이 작거나 다른 정보와 결합할 수 있다면 여전히 재식별될 수 있으므로 실제 데이터 범위를 기준으로 판단해야 합니다.

AI 분석에 필요하다면 **질병명, 심리 상태, 장애 유형은 유지**하고 이름, 주소, 기관명처럼 개인을 식별하는 정보는 마스킹합니다. 모든 민감한 단어를 삭제하면 분석 목적을 달성할 수 없고, 이름의 별칭이나 지역 정보를 남기면 재식별 위험은 줄지 않습니다. 따라서 민감도와 식별 가능성을 별도의 기준으로 처리합니다.

### 2. 가명정보를 익명정보로 취급하지 않습니다

이름을 `[대상자]`로 바꿔도 기관이 `[대상자]`와 실제 이용자를 연결하는 매핑 테이블을 보관한다면 해당 기록은 여전히 개인정보입니다. 따라서 **국외 이전 동의와 민감정보 처리 동의가 그대로 필요합니다.**

마스킹은 데이터가 노출되었을 때 개인을 바로 알아보기 어렵게 만들고, 기관이 적용한 안전조치를 입증하는 데 사용합니다. **동의를 대체하는 법적 근거가 아니라 동의와 함께 적용하는 추가 보호 조치**입니다.

### 3. 사후 탐지보다 기록 단계에서 직접 식별정보를 줄입니다

서술형 기록에서 개인을 식별할 수 있는 모든 표현을 자동으로 탐지하는 도구는 없습니다. 탐지 모델의 정확도를 높이는 것보다 기록 서식에서 실명 입력을 줄이는 편이 구현과 운영 비용이 낮습니다.

## 기록 서식에 역할 태그 적용

상담자가 기록을 작성할 때 실명 대신 **역할 태그**를 사용하도록 서식을 설계합니다.

```
[대상자], [모], [부], [조모], [자녀1], [자녀2], [담당], [협력기관1]
```

역할 태그를 사용하면 사후 마스킹에서 탐지해야 할 실명이 줄어듭니다. 또한 `PSEUDO_A7F3`처럼 의미가 없는 토큰보다 `[모]`, `[자녀1]`처럼 관계를 나타내는 태그가 AI가 가족 관계를 파악하는 데 유리합니다.

서식 변경은 `../assess/form-audit.md`의 양식 점검 단계에서 결정하고, 기록 테이블의 열은 `../data/ssot.md`에 따라 설계합니다. AI API로 전송할 가능성이 있는 기록이라면 처음부터 역할 태그를 적용해야 기존 기록을 다시 변환하는 작업을 줄일 수 있습니다.

## 마스킹할 항목과 유지할 항목

| 마스킹 또는 일반화 | 분석 목적상 유지 |
|---|---|
| 이름, 별칭, 줄임말(철수, 김씨, 큰애, 둘째, 할머니) | 질병명, 진단 |
| 주민번호, 전화, 계좌, 차량번호 | 심리 상태, 정서 |
| 주소, 동·리, 아파트 이름 | 장애 유형 |
| 학교·병원·기관 실명 → 종별로 ("초등학교", "정신건강복지센터") | 가구 형태 ("한부모, 자녀 2") |
| 정확한 날짜 → 월 단위 | 개입 내용, 경과 |
| 정확한 나이 → 5세 구간 | |
| 관할이 작으면 추가 적용: 장애 등급 → 구간, 질병명 → 상위 범주(KCD 3자리) | |

분석에 필요한 오른쪽 항목을 모두 삭제하면 AI 기능의 목적을 달성하기 어렵습니다. 반대로 왼쪽 항목이 남아 있으면 다른 정보와 결합해 개인을 식별할 수 있습니다. 마지막 행은 장애 유형과 질병명을 삭제하라는 의미가 아니라 `지체장애 3급`을 `지체장애, 중증`으로, `F32.1`을 `F32(우울 에피소드)`로 범주화하라는 의미입니다.

## 한국어 마스킹 시 추가로 처리할 항목

- **조사**: `김철수가`, `철수는`, `철수에게`처럼 이름에 조사가 붙은 형태도 탐지합니다. 역할 태그로 바꾼 뒤에는 받침에 맞게 이/가, 은/는 등을 조정합니다.
- **별칭과 관계 호칭**: 사례기록에는 `철수`, `김씨`, `큰애`, `둘째`, `할머니`처럼 명부의 이름과 다른 표현이 사용됩니다. 이용자 명부에서 별칭 사전을 함께 관리합니다.
- **작은 관할 지역**: 이름을 삭제해도 세부 지역, 나이, 가구 형태, 장애 유형의 조합으로 개인을 추정할 수 있습니다. 나이는 5세 구간, 지역은 시·군·구, 날짜는 월 단위로 일반화하고 실제 재식별 위험과 분석 품질을 표본으로 검증해 수준을 정합니다.

## 마스킹 이후에도 적용되는 의무

마스킹은 앞에서 설명한 협약, 계약, 동의, 개인정보 처리방침, 서버 검증을 대체하지 않습니다. 다음 세 가지를 주의하세요.

- **마스킹을 동의의 대체 수단으로 보지 않습니다.** 기관이 매핑 테이블을 보관하면 여전히 개인정보이므로 민감정보 처리와 국외이전에 필요한 동의를 확인합니다.
- **마스킹을 협약 적용 제외 근거로 보지 않습니다.** 지방자치단체와의 위수탁 협약이 가명정보의 반출도 제한하는지 원문을 확인합니다.
- **기업용 서비스라는 이유만으로 민감정보 처리가 허용된다고 가정하지 않습니다.** 사업자마다 표준 DPA의 민감정보 관련 문구와 추가 계약 조건이 다르므로 실제 사용할 서비스의 계약을 검토합니다.

미국의 보호건강정보를 처리하는 기관은 서비스별 BAA 제공 여부와 적용 기능을 추가로 확인할 수 있습니다. BAA는 미국 의료법을 위한 계약이므로 한국 개인정보보호법의 민감정보 동의와 국외이전 요건을 대체하지 않습니다.

## 마스킹과 AI 추론의 처리 위치

마스킹과 매핑 테이블을 이용한 복원 처리는 **국내 환경에서만** 수행합니다. 매핑 테이블과 암호화 키는 서로 다른 저장소에 보관합니다. AI API의 호출 위치나 클라우드 리전이 국내라고 해서 모델 추론까지 국내에서만 이루어진다고 가정해서는 안 됩니다.

다음 표는 2026년 9월 기준으로 주요 서비스의 국내 추론 고정 가능 여부를 확인한 결과입니다.

| 서비스 | 한국 안에서만 추론되나 | 확인 결과 |
|---|---|---|
| 앤트로픽 API | ❌ | `inference_geo`는 `global`(기본)·`us` 둘뿐. 저장은 미국 |
| AWS Bedrock 서울(ap-northeast-2) | ❌ | Claude는 **Global 추론 프로필만** 제공. Global은 "전 세계 상용 리전 어디든" 처리하고, 입력·출력이 다른 리전에 저장될 수 있음 |
| Azure Korea Central | ❌ | GPT 채팅 모델은 **지역 고정(Standard) 배포 없음.** APAC Data Zone만 |
| Google Vertex AI 서울(asia-northeast3) | 미확인 | Claude 리전 표를 확인하지 못했다. 글로벌 엔드포인트는 "특정 위치 처리를 보장하지 않음"이라고 명시 |

주요 세 업체의 모델 추론을 한국 리전으로만 고정하는 구성은 확인하지 못했습니다. 해외 AI API를 사용하는 앱은 국내 리전 이름만 근거로 국외 이전 검토를 생략하지 말고 **동의서 ③과 개인정보 처리방침에 국외 이전 내용을 반영**해야 합니다.

다음 조건에서는 국내 클라우드의 소형 오픈 모델이나 기관 내부 모델을 별도로 검토할 수 있습니다.

| 조건 | 권고 |
|---|---|
| 지자체 협약에 반출 제한이 있음 | 협약에서 국내 클라우드 사용도 제한하는지 확인한 뒤 국내 처리 서비스를 검토합니다. 클라우드 사용 자체가 제한되면 AI 기능을 제외합니다. |
| 국외 이전에 동의하지 않은 이용자가 많음 | 미동의 이용자의 기록만 국내 모델에서 처리하거나 기관 전체의 AI 처리 환경을 국내로 구성합니다. |
| 관할 지역이 작아 재식별 위험이 높음 | 처리 위치와 별개로 역할 태그와 일반화를 적용합니다. 국내에서 처리해도 재식별 위험은 남습니다. |

모든 처리를 국내에서 수행하면 국외 이전 요건은 제외할 수 있지만 민감정보 동의, 처리위탁 공개, 업체 계약, 지자체 협약, 2년간의 접근 로그 보관 요건은 그대로 적용됩니다.

## 자동 마스킹의 한계

> "작년에 아버지 돌아가시고 어머니가 요양원 가신 뒤로"

위 문장에는 이름이나 연락처가 없지만 가족의 사망과 시설 입소 시점이 결합되어 특정인을 알아볼 수 있습니다. 서술형 사례기록에는 정규식이나 NER이 찾기 어려운 간접 식별정보가 포함될 수 있으므로 자동 마스킹 결과를 익명정보로 간주해서는 안 됩니다. 계약과 동의 등 사전 조건을 충족하고 표본 검수를 운영하되, 마스킹된 데이터가 노출되어도 문제가 없다고 가정하지 않습니다.

## 하지 말 것

- 개인정보를 무료 등급 API로 전송하기. 유료 API의 계약과 데이터 처리 정책을 확인합니다
- 동의 상태를 클라이언트에서만 확인하기. 서버에서도 반드시 검증합니다
- 마스킹하지 않는 앱의 동의서에 "직접 식별정보를 제거하고 전송합니다"라는 문구를 남기기
- 분석 목적에 필요한 질병명과 심리 상태까지 일괄 삭제하기
- 마스킹했다는 이유로 동의를 생략하기. 재식별할 수 있는 가명정보는 여전히 개인정보입니다
- 통계·연구용 가명정보 특례(제28조의2)를 개별 이용자 서비스에 끌어오기
- 도구 하나의 결과를 믿고 표본 검수를 생략하기
- 기록 서식은 그대로 두고 사후 탐지 도구에만 의존하기
- AI 산출물을 확인 없이 법정 기록에 반영하기
- 요약 결과를 급여 판정이나 자격 결정에 연결하기
- 매핑 테이블과 암호화 키를 같은 저장소에 보관하기
- 조사 처리를 빼기 — "김철수가"를 놓칩니다

## 개발자·에이전트용 부록

다음 내용은 마스킹 파이프라인을 구현하는 개발자와 에이전트를 위한 설계 예시입니다. 비개발자는 건너뛰어도 됩니다. 기록 서식 단계부터 직접 식별정보를 줄이고, 규칙 기반 탐지와 NER, 일반화를 순서대로 적용합니다. 역할 태그를 사용하는 0단계를 생략하면 이후 탐지 단계에서 처리해야 할 표현이 크게 늘어납니다.

```
[기록 작성]        0단계  역할 태그 적용 — 실명 대신 역할 태그 사용
      ↓
[전처리 — 전량 국내]
                   1단계  사전 기반 결정적 치환 — 명부에서 사전 자동 생성
                   2단계  형식·체크섬 탐지 — 주민번호·전화·계좌·차량번호
                   3단계  공공 사전 매칭 — 학교·병원·복지시설·행정동
                   4단계  개체명 인식(NER) 잔여 탐지 — 두 모델의 탐지 결과 합집합
                   5단계  일반화 — 나이·지역·날짜·등급·질병명을 상위 범주로 변환
      ↓
[마스킹된 데이터] → AI API 호출 → [응답] → 복원(국내) → 담당자 검토
```

| 단계 | 도구 | 용도 및 주의사항 |
|---|---|---|
| 파이프라인 | Presidio | 1~4단계 탐지기를 Recognizer로 등록하고 Anonymizer에서 치환과 복원을 처리합니다. 기본 규칙은 미국 데이터 형식에 맞춰져 있으므로 국내 패턴을 별도로 구현합니다. 프로젝트 저장소 위치가 변경될 수 있어 설치 전에 공식 문서를 확인합니다. |
| 1단계 | pyahocorasick | 수천 개 항목의 다중 패턴 매칭에 사용합니다. |
| 2단계 | ko-pii | 규칙, 사전, 체크섬을 사용하므로 ML 모델이 필요하지 않습니다. 공개된 F1 점수는 대화체 0.66, 서식형 0.79이므로 주민번호·전화번호처럼 형식이 있는 식별자 탐지에만 사용합니다. |
| 4단계 | GLiNER 다국어 + KLUE-NER | 두 모델을 모두 실행하고 탐지 결과의 합집합을 사용합니다. 개인정보 탐지에서는 일부 일반 명사를 잘못 탐지하는 오탐보다 식별정보를 놓치는 미탐의 위험이 더 큽니다. 두 모델 모두 소형 모델이라 CPU에서 실행할 수 있습니다. |
| 5단계 | pseudonymizer | 개인정보위 가이드라인의 일반화·범주화 기법 구현 |
| 검증 | ARX | 실제 명부로 k-익명성을 계산합니다. k가 2~3처럼 낮게 나오면 해당 속성 조합의 일반화 수준을 높입니다. 계산 결과는 마스킹 기준을 정한 근거로 보관합니다. |
| API gateway | llm-guard | Presidio를 연결해 요청과 응답을 모두 검사하고 vault를 이용한 복원까지 처리합니다. AI API 호출 지점이 여러 곳일 때 검토합니다. |

### 역할 태그 설계

의미가 없는 토큰보다 가족이나 담당자 역할을 나타내는 태그가 관계 분석에 필요한 정보를 더 많이 유지합니다.

| 방식 | 예 | 판단 |
|---|---|---|
| 임의 토큰 | `PSEUDO_A7F3` | 관계 정보가 없어 관계 분석에 부적합 |
| 역할 태그 | `[대상자]`, `[모]`, `[자녀1]` | 권장 |
| 역할+해시 | `[모#3F]` | 같은 역할이 여럿일 때(외조모·친조모 등) |

여러 상담 기록에서 같은 사람에게 같은 태그를 부여해야 한다면 비밀 키를 사용하는 HMAC으로 결정적 치환을 구현합니다. 비밀 키는 매핑 테이블과 다른 저장소에 보관합니다.

```python
import hmac, hashlib
def token(name: str, case_id: str, role: str, secret: bytes) -> str:
    h = hmac.new(secret, f"{case_id}:{name}".encode(), hashlib.sha256)
    return f"[{role}#{h.hexdigest()[:4].upper()}]"
```

### 한국어 조사 처리

이름과 뒤에 붙은 조사를 함께 탐지하고, 역할 태그로 치환한 뒤 태그의 받침 여부에 따라 이/가·은/는·을/를을 다시 선택합니다.

```
(?P<name>김철수)(?P<josa>이|가|은|는|을|를|에게|께|와|과|도|만|의|씨|님)?
```

### 공공 사전

학교알리미의 학교 목록, 건강보험심사평가원의 요양기관 현황, 보건복지부의 사회복지시설 목록, 행정안전부의 법정동·행정동 코드를 기관명과 지역명 탐지에 사용할 수 있습니다. 데이터 출처와 갱신 주기를 기록하고 정기적으로 업데이트합니다.
