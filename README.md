# 사회복지 바이브코딩 스타터팩

> 코드 템플릿이 아니라, 코드를 짜기 전에 필요한 정보와 판단 근거를 정리한 문서 모음입니다.
> guide.md를 AI에게 주면, 무엇을 어디에 어떻게 만들지 함께 대화하며 정리할 수 있습니다.
> README.md 서문 외에는 저의 가이드에 따라 AI가 글을 쓰고 교정도 했습니다.

## 왜 만들었나

지금까지 우리는 내 손에 맞지도 않는 프로그램을 억지로 쓰고, 데이터가 흩어져 스스로 신뢰를 깎아먹으며, 불필요한 반복 행정에 소중한 시간과 에너지를 쏟아왔습니다. 정부가 의무 사용을 요구하는 프로그램은 업데이트도 안 되고, 업체가 만들어 주는 건 비싸다는 핑계 뒤에서 현장의 비효율과 무력감을 감내해 왔습니다.

제 생각에 바이브코딩은 그 자리를 되찾는 일입니다. 우리가 겪는 고통을 해결할 도구를 스스로 고르고, 그 도구를 운영할 규칙과 데이터 보호 장치를 동료들과 함께 정하고, 불편하면 내일 당장 함께 고쳐 쓰는 것. 실무자가 내 손에 맞는 도구를 직접 만드는 **현장 자율성과 도구 주권의 회복**입니다.

그런데 실제로 해 보면 걸림돌은 코딩 실력이 아닙니다. 오히려 GAS로 갈지 Cloudflare로 갈지, 개인정보는 어디에 저장해야 안전한지, 국외이전 동의는 받아야 하는지, 내가 그만두면 이 앱은 누가 맡는지. 코드는 AI가 짜 주지만 이런 선택은 사람 몫으로 남습니다. 그런데 선택지를 모르다보니 시행착오를 필요 이상으로 반복합니다.

이 저장소는 그 문턱을 낮추려고 만들었습니다. 개발을 몰라도 됩니다. 기관에서 바이브코딩으로 앱을 만들고자 할 때 판단에 필요한 것을 문서로 정리했습니다. 다 이해하지 못해도 됩니다. 그저 AI에게 그대로 전달하면 됩니다. 도움이 되시길 바랍니다.

앱을 만드는 것 자체가 목적이 아닙니다. 반복 행정을 줄여 당사자를 만날 시간을 되찾는 것이 목적입니다. 그래서 앱을 만들거나 자동화에 앞서 스스로에게 질문해야 합니다. 이 절차는 법령이나 지침에서 요구하는 일인가, 아니면 우리 기관의 관행일 뿐이라 없애도 되는 일인가? 없애고, 줄이고, 남는 것만 앱으로 만들면 좋겠습니다.

이를 위해 우리가 하는 일이 무엇인지 철저하게 규명하고 객관적으로 분석해야 합니다. 흔히 SOP를 작성한다고 하는데, 많은 기관은 이 과정 없이 앱을 만들기 시작합니다. 그래서 실제 SOP를 작성하고 그 과정에서 데이터베이스를 설계하는 절차를 넣었습니다.

그런데 막상 기관에서 하려고 하면, 생각보다 저항이 심합니다. 당장 일이 많아지는 것 같기도 하고, 기존에 하던 방식이 마치 잘못된 것처럼 느껴지도록 메시지를 잘못 전하기도 하는 것 같습니다. 저는 그것이 사회복지 현장에서 ‘문제를 문제라고 정의하는 것’ 자체를 터부시하고, 익숙하지 않은 건 아닐까 생각합니다.

사회복지에서는 강점관점이 굉장히 중요합니다. 그런데 이런 관점에 익숙해지다 보니, 조직의 업무나 시스템을 볼 때도 ‘문제’라는 말을 너무 조심하게 되는 경우가 있는 것 같습니다.

“그래도 잘하고 있는 부분이 있는데”, “현장에서는 다 사정이 있는데”, “문제라고 표현하기는 조금 그렇고…” 하다 보면 정작 무엇을 바꿔야 하는지가 흐려지기도 하고요.

그런데 DX·AX나 업무개선을 하려면 결국 지금 무엇이 불편한지, 어디에서 오류나 누락이 생기는지, 왜 같은 일이 반복되는지를 집요하고, 또 아프도록 명확하게 정의해야 합니다. 문제를 선명하게 정의하지 못하면 AI를 붙이든 시스템을 만들든 결국 어렵습니다.

중요한 건 사람을 문제로 보는 것과 시스템의 문제를 찾는 것은 전혀 다르다는 것입니다.

예를 들어
“담당자가 자꾸 누락한다”라고 하면 개인의 문제가 되지만,
“현재 업무가 담당자의 기억과 경험에 의존하고 있고 누락을 막아주는 절차가 없다”라고 보면 시스템의 문제가 됩니다.

후자의 방식이 오히려 사람을 탓하지 않으면서도 조직을 바꿀 수 있는 접근이 아닐까 싶습니다.

그래서 사람에게는 강점관점, 시스템에는 문제해결관점으로 구분하면 좋을 것 같아요.
당사자나 직원을 문제로 규정하지는 않되, 당사자와 직원이 불편을 겪게 만드는 절차와 구조의 문제는 오히려 더 정확하게 찾아야 하지 않을까 싶습니다.

그리고 한 걸음 더 나아간다면, 조직 안에서 만들 수 있는지 묻기 전에 만들어도 되는지 물어보면 좋겠습니다. 근태를 정확히, 그리고 편리하게 관리하고자 지문등록 출근앱을 만들어도 된다는 뜻은 아닙니다. 목적이 옳다고 모든 수단이 정당해지는 것은 아니니까요.

앱을 만들기 전에 따져 볼 다섯 가지 질문을 [`ethics.md`](ethics.md)에 모았습니다. 어떤 위험과 부담이 있는지 알고 결정하기 위한 것입니다.

모든 문서는 개발 지식이 없는 독자를 기준으로 썼고, 낯선 용어는 [`glossary.md`](glossary.md)에 풀어 두었습니다. AI도 `guide.md`를 바탕으로 코딩을 할 때, 용어를 설명하며 작업하도록 했습니다.

## 사용방법

### Claude Code 같은 도구를 쓴다면

저장소 링크를 복사해서 AI에게 제공하면 준비는 끝납니다. 물론 Opus, Sol 같은 상위 모델 사용을 권장합니다. 왜냐하면 이 저장소는 일종의 Harness이며 상위 모델일수록 지시를 잘 따르기 때문입니다.

```
https://github.com/YW-Rainbow/welfare-vibecoding-starter.git
```

이후 만들고 싶은 앱의 목적과 현재 업무 절차를 설명하면 됩니다. 처음부터 요구사항을 완벽하게 정리할 필요는 없습니다.

> "우리 기관 프로그램일지 앱을 만들려고 해. 사진도 회기당 2~3장 올라가."

Claude Code나 Codex 같은 에이전트형 도구가 이 저장소를 열면 `CLAUDE.md` 또는 `AGENTS.md`를 먼저 읽습니다. 두 파일에는 앱을 만들기 전에 확인해야 할 질문과 작업 순서가 들어 있습니다. 에이전트는 먼저 그 업무가 꼭 필요한지 확인하고, 저장할 데이터와 사용자, 사용 환경 등을 물어본 뒤 적합한 플랫폼을 추천합니다. 판단이 끝나면 사용자에게 확인받은 뒤 이 폴더를 앱 프로젝트로 바꿉니다. 어떤 판단을 거쳐 이 경로를 골랐는지 `DECISION.md`에 기록하고, 원래 저장소의 원격 연결을 끊은 다음 선택한 경로의 규칙과 운영에 필요한 문서만 남기고 개발을 시작합니다.

### 채팅창에서 쓴다면

일반 채팅창에서는 AI가 이 저장소의 파일을 자동으로 읽지 못하므로 `guide.md`를 직접 전달해야 합니다. [`guide.md`를 여기서 다운로드해](https://raw.githubusercontent.com/YW-Rainbow/welfare-vibecoding-starter/main/guide.md)(링크를 열고 우클릭한 뒤 다른 이름으로 저장) Claude나 ChatGPT 대화창에 첨부하거나, 파일 내용을 대화창에 붙여 넣으세요. 그런 다음 만들고 싶은 앱을 이야기하면 됩니다. 판단 과정에서 다른 문서가 필요해지면 AI가 파일 이름과 다운로드 주소를 알려 줍니다.

어느 방법을 사용하든 모르는 기술 용어가 나오면 [`glossary.md`](glossary.md)를 확인하세요. 이 저장소에서 사용하는 주요 용어를 개발 지식이 없는 사람도 이해할 수 있도록 설명했습니다.

### 서식 전체를 정리하고 싶다면

앱 하나가 아니라 기관의 양식과 업무 전체를 정리하고 싶다면 [`form-audit.md`](form-audit.md)에서 시작하세요. 양식을 하나씩 보면 모두 필요한 것처럼 보이기 때문에, 기관에서 사용하는 양식을 한곳에 모아 같은 기준으로 살펴봐야 합니다. 각 양식의 근거와 실제 독자, 법정서식 여부, 데이터를 반복해서 기록하고 집계하는지를 차례로 확인하면 없앨 양식, 그대로 둘 양식, 앱으로 만들 양식을 구분할 수 있습니다. 불필요한 양식을 없애거나 합치는 것이 첫 번째 성과이고, 앱으로 전환하기로 한 양식만 `guide.md`의 판정 절차로 넘어갑니다.

앱을 여러 개 만들 계획이거나 담당자마다 별도의 파일로 이용자 정보를 관리하고 있다면 [`ssot.md`](ssot.md)를 먼저 확인하세요. 이용자 명부를 하나의 원본으로 정하지 않은 채 앱만 늘리면 같은 어르신이 파일마다 서로 다른 이름으로 기록되고, 나중에는 담당자가 자료를 일일이 대조해야 합니다. 이용자는 명부에서만 등록하고, 각 앱의 기록은 이용자 이름이 아니라 이용자 ID로 연결하는 것이 핵심입니다.

## 플랫폼 선택 기준

이 저장소는 어느 플랫폼이 가장 좋다고 순위를 정하지 않습니다. 기관이 지켜야 할 요건은 플랫폼이 아니라 개인정보보호법과 실제 운영 환경에서 정해지기 때문입니다. 어떤 플랫폼을 선택하더라도 사용자 인증, 데이터 접근 권한, 백업, 보존기간이 지난 개인정보의 파기 같은 일은 반드시 해야 합니다.

다만 플랫폼마다 이 요건을 충족하는 방법은 다릅니다. 서비스 업체가 기본으로 제공하는 기능도 있고(◎), 사용자가 설정해야 하는 기능도 있으며(○), 직접 개발하고 테스트해야 하는 기능도 있습니다(△). 접근 기록을 점검하고 파기 대장을 작성하며 동의서와 인수인계를 관리하는 일처럼 기관의 담당자가 계속 챙겨야 하는 업무도 있습니다(●). `guide.md`의 요건 매트릭스는 플랫폼을 선택했을 때 어떤 일이 기관의 몫으로 남는지 비교하기 위해 만든 표입니다.

## 기여

- **플랫폼 추가** — 요건 매트릭스에 열 하나를 더하고, `rules/`에 해당 규칙 파일 하나를 추가합니다. 이것이 플랫폼을 추가하는 기본 단위입니다.
- **스타터 템플릿 추가** — 경로별 스타터 템플릿 저장소를 만들어 링크해 주세요. `apps-script-vibe-starter`를 참고할 수 있습니다.
- **정보 업데이트** — 가격, 무료 한도, 관련 제도는 자주 바뀝니다. 문서의 기준일을 확인하고 이슈나 PR로 알려 주세요.
- **현장 사례** — 사용한 구성, 만든 앱, 운영 과정에서 발생한 문제와 해결 방법을 공유해 주세요.
