# Cloudflare Pages + Supabase 서울 리전 개발 기준(경로 A)

> 출처·최신판: https://github.com/YW-Rainbow/welfare-vibecoding-starter
> 적용 대상: 개인정보를 다루는 중규모 이상의 앱
> 기본 구성: Supabase 서울(`ap-northeast-2`) 리전. Free와 Pro는 백업, 서비스 중단, 용량과 운영 조건을 확인해 선택합니다.
> 기준일: 2026-08
> 이 문서는 `agentic.md`와 함께 적용합니다.

아래 구성은 개인정보 처리 사업자와 경로를 줄이기 위한 권장 기본값입니다. 다른 구성을 사용하려면 개인정보 처리 위치, 접근 권한, 로그, 백업과 파기에서 같은 결과를 충족하는지 설명하고 검증합니다.

## 권장 아키텍처

```
브라우저 ── supabase-js ──→ Supabase 서울(DB·Auth·Storage)   ← 개인정보 처리
브라우저 ←── Cloudflare Pages(정적 파일 제공)                 ← 개인정보 없음
브라우저 ──→ Cloudflare Workers(공개 데이터·통계 API)         ← 개인정보 없음
```

- 기본 구성에서는 개인정보를 브라우저에서 Supabase로 직접 전송해 중간 처리자를 늘리지 않습니다. 업무 규칙상 서버가 필요하다면 실행 위치를 고정할 수 있는 서버를 사용하고 데이터 흐름을 문서화합니다.
- 서버 로직이 필요하면 Supabase Edge Functions를 사용하고 모든 호출에 서울 리전을 명시합니다: `supabase.functions.invoke('fn', { region: 'ap-northeast-2' })`.
- 호출 헤더를 설정하기 어려운 webhook에는 `?forceFunctionRegion=ap-northeast-2`를 사용합니다. 리전을 지정하지 않은 Edge Function에 개인정보를 전송하지 않습니다.

## RLS

1. 개인정보를 저장하는 모든 테이블에서 RLS를 활성화합니다.
2. 명시적으로 허용한 접근만 가능하도록 deny-by-default 원칙을 적용합니다.
3. 정책은 기관 소속과 담당 업무를 기준으로 작성합니다. 예를 들어 `auth.uid()`가 해당 행의 담당자이거나 같은 기관 소속일 때만 조회를 허용합니다.
4. `service_role` 키는 프론트엔드 코드와 공개 저장소에 넣지 않습니다. 브라우저에는 anon key만 사용하고 실제 접근 권한은 RLS가 검사합니다.
5. 테이블을 만들 때 RLS 정책과 권한 테스트를 함께 작성합니다. 다른 계정으로 권한이 없는 행을 조회했을 때 거부되는지 자동 테스트에 포함합니다.

## 파일 저장소

1. 사진과 파일을 base64로 변환해 데이터베이스에 저장하지 않습니다. Storage 버킷에 파일을 저장하고 데이터베이스에는 경로와 메타데이터만 기록합니다.
2. 버킷은 private으로 만들고 유효기간이 1시간 이내인 signed URL로만 조회합니다.
3. 별도 요구가 없다면 업로드 전에 브라우저에서 긴 변 1600px, WebP 품질 80으로 압축하고 320px 썸네일을 생성하는 값을 출발점으로 사용합니다. 원본 보존, 인쇄 품질과 네트워크 환경에 따라 값을 바꿀 수 있습니다.
4. 파일 경로는 보관 기간이 끝난 파일을 범위별로 찾을 수 있어야 합니다. `{연도}/{프로그램ID}/{회기}/{uuid}.webp`는 한 가지 예시입니다.
5. Storage 정책에도 데이터베이스와 같은 기관·담당자 기준의 접근 권한을 적용합니다.

## 삭제 완결성

1. 데이터베이스 테이블은 FK와 `ON DELETE CASCADE`를 사용해 일지를 삭제할 때 첨부 파일의 메타데이터 같은 연결 기록도 처리되도록 설계합니다. 결재와 감사 이력처럼 보존해야 하는 기록에는 CASCADE를 적용하지 않습니다.
2. Storage 파일은 데이터베이스의 CASCADE로 삭제되지 않으므로 삭제 함수에서 명시적으로 제거합니다. 행 삭제 뒤 연결 파일이 남지 않는지 테스트합니다.
3. 개인정보 테이블에 `retention_until` 컬럼을 두고 `pg_cron`으로 보관 기간이 끝난 데이터를 정기적으로 파기합니다.
4. 동의 철회나 삭제 요청은 사용자 확인, 해당 정보주체의 행·파일·계정 처리, 파기 대장 기록까지 하나의 절차로 구현합니다. 법적 보존 의무가 있는 기록은 즉시 삭제 대상과 구분합니다.

## 접근 로그

- 개인정보의 조회·수정·삭제·출력을 `access_log` 테이블에 `[접속 일시, auth.uid(), 수행 업무, 대상 행 ID]` 형식으로 기록합니다.
- 브라우저에서 Supabase로 직접 요청하는 구조에서는 앱 테이블에 접속지 IP를 기록하기 어렵습니다. Supabase API 로그의 보관 범위와 한계를 확인하고 내부관리계획에 기록합니다.
- 데이터 조회는 접근 로그를 남기는 데이터베이스 함수 또는 이에 준하는 서버 로직을 통해 처리합니다. `access_log`에는 INSERT만 허용하고 UPDATE와 DELETE를 차단하며 관리자만 조회할 수 있도록 RLS를 적용합니다.
- 개인정보 원본의 보관 기간이 끝나도 접속기록의 법정 보관 기간이 남아 있으면 로그를 삭제하지 않습니다. 원본 데이터와 로그의 파기 주기를 분리합니다.
- 이상 조회를 확인하는 정기 점검 일정을 기관 캘린더에 등록합니다.

## 백업

- Supabase Pro의 자동 데이터베이스 백업이 활성화되어 있는지 확인하고 실제 복구 테스트를 수행합니다.
- 기본 데이터베이스 백업에는 Storage 파일이 포함되지 않으므로 버킷 복제나 별도 다운로드 등 파일 백업 절차를 마련하고 `../ops/handover.md`에 기록합니다.

## Google Sheets를 보조 도구로 사용하기

Supabase Table Editor는 데이터를 조회하고 수정할 수 있지만 Google Sheets처럼 셀 수식을 바로 사용할 수는 없습니다. 반복되는 집계는 데이터베이스 뷰로 만들고, 일회성 분석은 필요한 데이터만 Google Sheets로 가져와 처리합니다.

자주 사용하는 실인원·연인원 집계는 뷰로 정의합니다. 원본이 변경되면 뷰의 조회 결과도 함께 갱신됩니다.

```sql
CREATE VIEW v_실적_연간 AS
SELECT 연도, 프로그램, 성별, 연령대,
       COUNT(DISTINCT 이용자ID) AS 실인원,
       COUNT(*)                 AS 연인원
FROM 참여기록
GROUP BY 연도, 프로그램, 성별, 연령대;
```

일회성 계산에는 GAS로 `현재 데이터 가져오기` 기능을 만들어 필요한 데이터만 시트에 복사할 수 있습니다. 이때 원본은 Supabase이고 시트는 계산과 보고서 작성을 위한 임시 작업 공간입니다. 시트에 개인정보가 포함되면 해당 파일도 보호 대상이므로 공유 권한과 보관 기간을 제한하고 작업이 끝나면 정해진 절차에 따라 삭제합니다.

## 운영 규칙

- Supabase 프로젝트와 Cloudflare 계정은 개인 계정이 아니라 기관이 관리하는 계정으로 생성합니다.
- 후임자가 데이터를 확인할 수 있도록 Supabase Table Editor의 위치와 기본 사용법을 인수인계합니다.
- 개인정보 처리방침과 위탁 문서에 실제 수탁자와 처리 내용을 반영합니다. DPA 체결 절차는 `../ops/consent-notes.md`를 참고합니다.
