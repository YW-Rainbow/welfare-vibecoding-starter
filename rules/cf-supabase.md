> 기준일: 2026-08

## 아키텍처 (변경 금지)

```
브라우저 ── supabase-js ──→ Supabase 서울 (DB·Auth·Storage)   ← 개인정보 경로
브라우저 ←── CF Pages (정적 파일 배달만)                        ← 개인정보 없음
브라우저 ──→ CF Workers (공개 데이터·통계 API만)                ← 개인정보 없음
```

- **개인정보는 브라우저에서 Supabase로 직행한다.** CF Workers 등 중간 서버를 거치지 않는다.
  (근거: 수탁자 1곳 원칙 + 글로벌 엣지에서의 개인정보 처리 회피 — guide.md 원칙 1·2)
- 서버 로직이 필요하면 Supabase Edge Functions를 쓰되, **모든 호출에 리전을 명시**한다:
  `supabase.functions.invoke('fn', { region: 'ap-northeast-2' })`
  헤더를 못 붙이는 웹훅 등은 `?forceFunctionRegion=ap-northeast-2`.
  리전 미지정 호출로 개인정보를 보내는 코드는 작성 금지.

## RLS (가장 중요)

1. **모든 테이블에 RLS를 활성화한다.** RLS 없는 테이블에 개인정보 저장 금지.
2. **deny-by-default**: 정책이 없으면 아무도 못 읽는 상태가 기본. 필요한 접근만 정책으로 연다.
3. 정책은 소속·담당 기준으로: 예) `auth.uid()`가 해당 행의 담당자이거나 같은 기관 소속일 때만.
4. `service_role` 키는 절대 프론트엔드 코드·공개 저장소에 넣지 않는다. anon 키만 클라이언트에.
5. 스키마 생성 시 각 테이블마다 RLS 정책을 함께 생성하고, "다른 계정으로 남의 행 조회 시도"
   테스트를 반드시 포함한다.

## Storage (사진·파일)

1. 파일을 DB에 넣지 않는다(base64 금지). 버킷 + DB에는 경로만.
2. 버킷은 **private** 생성. 조회는 signed URL(만료 1시간 이내)로만.
3. 업로드 전 클라이언트 압축: 긴변 1600px, WebP, 품질 80. 썸네일(320px) 동시 생성 2벌 저장.
4. 경로: `{연도}/{프로그램ID}/{회기}/{uuid}.webp` — 만기 파기를 폴더 단위로.
5. Storage 정책도 RLS와 같은 기준(소속 기관 폴더만).

## 삭제 완결성

1. 스키마는 FK + `ON DELETE CASCADE`로 설계한다 (일지 삭제 → 첨부 메타 자동 삭제).
2. Storage 파일은 cascade가 안 되므로, 삭제 함수에서 명시적으로 함께 제거하고
   삭제 테스트(행 삭제 후 파일 잔존 여부 확인)를 포함한다.
3. 모든 개인정보 테이블에 `retention_until` 컬럼. pg_cron으로 만기 배치 파기.
4. 철회 처리: Auth 본인 확인 → 해당 주체의 행+파일+계정 일괄 삭제 → 파기 대장 기록.

## 접근 로그 (접속기록 — 고시 제8조)

- 개인정보 조회·수정을 담는 `access_log` 테이블:
  `[접속 일시(now()), auth.uid(), 수행 업무, 처리한 정보주체(대상 행)]`.
  (접속지 IP는 브라우저 직행 구조상 앱 테이블에서 확보 어려움 — Supabase API 로그가
  보조 기록이 되나 보존기간이 짧으므로, 한계를 내부관리계획에 명시)
- 트리거 또는 조회 함수(SECURITY DEFINER) 경유로 기록. INSERT만 허용하고
  UPDATE/DELETE는 차단. 로그 테이블 자체도 RLS(관리자만 열람).
- 보관: 민감정보 처리 시스템은 **2년 이상** (기본 1년). `retention_until` 만기 파기
  배치가 `access_log`를 건드리지 않게 — 데이터를 파기해도 접속기록은 보존기간 동안
  유지하고, 로그 자체의 파기는 별도 주기로.
- 점검: 월 1회 이상(현행 기준) 이상 조회 여부 확인을 기관 캘린더에 등록.

## 시트로 내려받아 계산하기

구글시트를 쓰다 옮겨 온 기관이 가장 아쉬워하는 것은 "옆 칸에 함수 붙여
즉석에서 계산하기"입니다. Table Editor는 원본을 보고 고치는 것까지는 되지만
셀 함수는 없습니다. 두 가지로 메웁니다.

**집계는 뷰로 붙박이를 만든다.** 자주 쓰는 계산은 뷰(view)로 만들어 두면
Table Editor에 표가 하나 더 생긴 것처럼 보이고, 원본이 바뀌면 자동으로
갱신됩니다. 실인원·연인원처럼 매년 같은 형태로 뽑는 것은 뷰로 두세요.

```sql
-- 예: 프로그램별 성별·연령대 실인원/연인원
CREATE VIEW v_실적_연간 AS
SELECT 연도, 프로그램, 성별, 연령대,
       COUNT(DISTINCT 이용자ID) AS 실인원,
       COUNT(*)                 AS 연인원
FROM 참여기록
GROUP BY 연도, 프로그램, 성별, 연령대;
```

**즉석 계산은 시트를 작업대로 쓴다.** GAS 스크립트로 "지금 데이터 가져오기"
버튼을 만들어 두면, 필요할 때 눌러 시트에 붓고 늘 하던 대로 함수를 씁니다.
원본은 Supabase에 있고 시트는 계산과 보고서 작성용 작업대가 됩니다.
시트를 DB로 쓰는 것이 문제였지 계산 도구로 쓰는 것은 문제가 아닙니다.

주의: 내려받은 시트에 개인정보가 담기면 그 시트도 보호 대상입니다.
공유 대상을 두지 말고, 보고서를 만든 뒤에는 지우세요.

- Table Editor가 관리 UI 역할을 한다 — 후임자 인계 시 여기부터 보여줄 것.
