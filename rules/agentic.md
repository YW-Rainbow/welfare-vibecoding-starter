# 에이전트형 개발·배포의 안전 경계

> 출처·최신판: https://github.com/YW-Rainbow/welfare-vibecoding-starter
> 적용 대상: Claude Code, Codex처럼 프로젝트 파일을 수정하고 명령 실행과 배포까지 수행하는 에이전트형 AI 도구
> 사용자는 개발 지식이 없다고 가정합니다. 전문용어가 처음 나오면 `../docs/glossary.md`의 설명을 참고해 한 문장으로 풀어서 설명하세요.

이 파일은 선택한 플랫폼 문서와 함께 새 앱 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 반영합니다. 이 문서는 에이전트의 작업 순서를 지정하지 않습니다. 아래 안전 경계와 완료 조건 안에서 조사, 구현, 도구 선택과 검증 방법은 에이전트가 작업 규모와 위험에 맞게 정합니다.

## 자율적으로 진행할 범위

- 사용자의 목적과 기존 프로젝트에서 작업 범위를 추론하고, 되돌릴 수 있는 조사·구현·수정은 별도 승인 없이 진행합니다.
- 결과를 크게 바꾸는 정보가 빠져 있을 때만 질문합니다. 질문하기 전에는 읽기와 분석 등 이미 허용된 일을 먼저 진행해 사용자가 검토할 수 있는 구체적인 안을 만듭니다.
- 현재 요구를 충족하는 가장 단순한 구조를 선택합니다. 요청하지 않은 기능, 미래를 가정한 추상화, 불필요한 새 도구와 서비스를 추가하지 않습니다.
- 아래에 적힌 구현 예시는 목적을 달성하는 한 다른 방법으로 바꿀 수 있습니다. 안전 경계를 다른 방식으로 충족했다면 선택 이유와 검증 결과를 남깁니다.

## 운영 데이터를 에이전트에게 제공하지 않습니다

에이전트가 운영 데이터베이스를 조회하거나 실제 이용자 정보가 포함된 파일을 읽으면 그 내용이 AI 서비스 제공자에게 전송될 수 있습니다. 앱의 AI 분석 기능에 대한 동의를 받았더라도 개발 도구의 대화 컨텍스트에 개인정보를 제공해도 된다는 뜻은 아닙니다.

- 개발·디버깅·테스트에는 가상 데이터인 **시드 데이터**만 사용합니다. `seed.sql`이나 시드 스크립트를 프로젝트에 포함합니다.
- 운영 데이터베이스의 접속 정보는 에이전트에게 제공하지 않습니다. 개발용 프로젝트나 브랜치 데이터베이스를 분리하고 개발용 인증 정보만 사용합니다.
- 운영 장애를 조사할 때는 오류 로그에서 개인정보를 제거하거나 마스킹한 뒤 전달합니다. 가능하면 같은 상황을 시드 데이터로 재현합니다.
- 스크린샷, CSV, 로그 파일을 에이전트에게 제공하기 전에 개인정보가 포함되어 있는지 확인합니다.

## 인증 정보에는 최소 권한을 적용합니다

에이전트가 사용하는 토큰의 권한 범위가 넓을수록 사고가 발생했을 때 영향을 받는 범위도 커집니다.

- 배포 토큰은 해당 프로젝트에 필요한 권한만 포함해 발급합니다. 계정 전체에 접근할 수 있는 토큰은 사용하지 않습니다.
- `service_role` 키와 관리자 키는 에이전트의 환경변수에 넣지 않습니다. RLS를 우회하는 키가 필요하다는 제안이 나오면 먼저 권한 설계를 다시 검토합니다.
- 인증 정보는 `.env`나 시크릿 저장소에서 관리합니다. 키가 코드, 커밋, 로그에 노출되면 즉시 해당 키를 폐기하고 다시 발급합니다. `.gitignore`에 `.env*`와 `.clasprc.json`이 포함되어 있는지 확인합니다.
- 사용하지 않는 장기 토큰은 정기적으로 폐기합니다. 점검 주기를 기관 캘린더와 인수인계 문서에 기록합니다.

## 위험에 비례해 검증합니다

사람이 모든 코드를 검토하기 어려우므로 배포 전에 중요한 실패를 잡을 증거가 필요합니다. 변경 규모와 데이터 등급에 맞는 테스트, 정적 검사 또는 수동 점검을 선택합니다. 작은 문구 수정에 전체 회귀 테스트를 요구하지 않고, 개인정보의 권한·삭제·로그처럼 실패 영향이 큰 기능은 자동 테스트를 우선합니다.

당사자가 직접 사용하는 화면은 `../docs/requirements/design.md`의 배포 전 체크리스트를 함께 적용합니다. 키보드 조작, 포커스 표시, `label`, 색 대비, 200% 확대를 확인합니다. 종이나 엑셀로 출력하는 기록은 `../docs/requirements/print.md`의 한글 글꼴, 페이지별 머리글, 서식 칸 수, 개인정보 열 기본 제외, 출력·반출 기록도 확인합니다.

개인정보를 다루는 앱에서 관련 기능이 있을 때 확인할 항목:

- [ ] RLS·권한: 다른 계정으로 권한이 없는 행을 조회하면 거부되는가
- [ ] 파일 저장소: public URL로 접근하면 거부되고 유효기간이 있는 signed URL만 허용되는가
- [ ] 삭제 완결성: 레코드를 삭제한 뒤 연결 파일과 파생 데이터가 남지 않는가
- [ ] 접근 로그: 조회·수정·삭제·출력 내역이 기록되고 로그의 임의 수정과 삭제가 차단되는가
- [ ] 시크릿 검사: 빌드 결과와 Git 이력에 API 키나 토큰이 포함되지 않았는가

반복해서 확인해야 하는 항목은 배포 파이프라인에 포함합니다. 적용되지 않는 항목은 억지로 구현하지 않고 제외 이유를 기록합니다.

## 되돌리기 어려운 작업은 확인 후 실행합니다

다음 작업은 대상, 영향, 복구 방법을 확인하고 사용자의 명시적인 승인을 받은 뒤 실행합니다. 승인받았고 실행 환경의 권한과 보호 장치가 충분하다면 에이전트가 수행할 수 있습니다. 운영 데이터 전체나 계정 자체를 없애는 작업은 가능하면 사용자가 관리 콘솔에서 직접 실행합니다.

- 운영 데이터베이스의 `DROP`, `TRUNCATE`, 대량 `DELETE`, 운영 마이그레이션 적용
- 버킷·프로젝트 삭제와 도메인·DNS 변경
- 결제 플랜 변경과 토큰·API 키의 발급·폐기

## 변경 이력과 인수인계 절차를 저장소에 남깁니다

에이전트와의 대화는 인수인계 자료가 될 수 없습니다. 후임자가 작업을 이어갈 수 있도록 코드, 규칙, 실행 절차를 저장소에 기록합니다.

- 소스와 설정은 Git으로 관리합니다. 사용자가 커밋을 요청했거나 기존 작업 흐름에 커밋이 포함되어 있다면 무엇을 왜 바꿨는지 알 수 있는 메시지를 사용합니다.
- 프로젝트의 `CLAUDE.md`나 `AGENTS.md`에 이 파일과 선택한 플랫폼 규칙을 포함합니다. 후임자가 같은 규칙을 읽고 작업을 재개할 수 있어야 합니다.
- `../ops/handover.md`에는 사용한 AI 도구, 규칙 파일, 실행 명령, 인증 정보의 보관 위치를 기록합니다. 인증 정보 자체는 문서에 적지 않습니다.

## 사용자와 에이전트의 결정 범위를 구분합니다

사용자는 단순한 승인자가 아니라 앱의 목적과 범위를 정하는 사람입니다. 에이전트는 구현 방법을 제안하고 위험과 대안을 설명하지만, 기관의 정책 결정을 대신하지 않습니다.

다음 사항은 사용자가 결정합니다.

- 앱을 만드는 목적과 포함하거나 제외할 업무
- 기획 확정과 배포 여부
- 앱을 만들지 않거나 기존 절차를 폐지하는 결정

사용자의 목적, 현장에 관한 설명과 명시적인 결정은 일반적인 개발 권장사항보다 우선합니다. 개인정보 보호, 법적 의무, 보안 또는 되돌리기 어려운 영향과 충돌할 때만 구체적인 근거와 대안을 설명하고 확인합니다. 단순한 기술 취향을 이유로 사용자의 결정을 뒤집지 않습니다.

요청을 그대로 구현할 수 없다면 고정된 형식을 채우기보다 이유, 요청의 목적, 같은 목적을 달성할 대안을 간결하게 설명합니다.

다음 요청은 사용자 지시가 있어도 위험을 확인하지 않은 채 실행하지 않습니다. 구체적인 위험과 더 안전한 대안을 설명하고 필요한 결정을 받습니다.

- RLS나 서버의 권한 검사를 끄는 작업
- `service_role` 키나 관리자 키를 프론트엔드 코드 또는 에이전트 환경에 넣는 작업
- 실제 이용자의 데이터를 에이전트 대화에 제공하는 작업
- 운영 데이터베이스에 마이그레이션이나 대량 삭제를 바로 적용하는 작업
- 접근 로그를 삭제하거나 기록 기능을 끄는 작업
- 지문·얼굴 같은 생체인식정보를 수집하는 기능을 `../docs/assess/ethics.md`의 검토 없이 만드는 작업

새로운 외부 서비스 연동, 되돌리기 어려운 데이터 구조 변경, 예상하지 못한 비용, 개인정보 항목 추가·변경이 기존 요청에서 승인되지 않았다면 영향과 선택지를 설명하고 확인을 받습니다. 이미 사용자가 선택했거나 요구사항에 포함된 사항은 반복해서 승인받지 않습니다.
