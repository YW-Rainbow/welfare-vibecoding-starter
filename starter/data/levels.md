# 기관의 앱과 데이터 관리 수준을 정하는 다섯 단계

> 출처·최신판: https://github.com/YW-Rainbow/welfare-vibecoding-starter
> 이 문서는 개별 앱의 구현 방법이 아니라 기관 전체의 앱과 데이터 관리 범위를 정하는 기준입니다. 단계가 높다고 항상 좋은 것은 아니며 기관의 규모, 인력, 해결할 문제에 맞는 단계가 적절합니다.
> 4단계는 신용우의 「AI 시대를 위한 데이터 설계 방법론」 1~6편(2026.3~5)을 이 저장소에 맞게 요약하고, 개체와 관계의 종류, 기준 선정 규칙, 저장 방식을 보충했습니다. 원문은 아래의 읽을거리를 참고합니다.
> 앱 하나의 구현보다, 앱이 세 개 이상이거나 인수인계, 기관 공통 데이터, 관계 데이터, 판단 기준을 논의할 때 사용하는 문서입니다.

## 기관마다 필요한 단계가 다릅니다

바이브코딩으로 만든 앱이 늘어나면 특정 담당자가 퇴사했을 때 오류 수정과 기능 변경이 어려워질 수 있습니다. 이 문제에 대응하는 방법은 크게 두 가지입니다.

- 전담 개발자가 없는 기관은 필요한 앱을 작은 범위로 만들고, 후임자가 AI를 사용해 다시 만들 수 있도록 판단 기록, 요구사항, 운영 절차를 남깁니다.
- 데이터 구조와 권한을 관리할 담당자가 있는 기관은 여러 앱이 함께 사용하는 공용 데이터 레이어와 API를 운영할 수 있습니다.

두 방법 모두 특정 담당자의 기억과 개인 계정에 의존하지 않는 것이 목적입니다. 전자는 앱을 다시 만들 수 있는 문서를 인수인계하고, 후자는 앱과 분리된 공용 데이터 구조와 접근 권한을 인수인계합니다.

## 단계별 비교

다음 단계로 이동하면 관리 대상과 담당 역할이 추가됩니다. 상위 단계로 이동해도 당사자를 위한 종이, 전화, 대면 신청 방식이 필요하다면 계속 유지합니다.

| 단계 | 주요 구성 | 다음 단계를 검토할 조건 | 필요한 역할 | 인수인계 자료 | 관련 문서 |
|---|---|---|---|---|---|
| 0 | 담당자별 종이와 엑셀 | 반복 업무를 구조화할 필요가 생김 | 별도 역할 없음 | 기존 문서와 파일 목록 | `../assess/form-audit.md` |
| 1 | 반복 기록을 행과 컬럼으로 구조화한 앱 하나 | 같은 데이터를 반복해서 집계함 | 업무 담당자 | 앱, `DECISION.md`, `../requirements/requirements.md` | `../workflow.md` |
| 2 | 모든 앱이 참조하는 이용자 명부와 이용자 ID | 같은 명부를 두 곳 이상에 입력함 | 명부 관리자 | 이용자 명부, ID 규칙, 연결된 앱 목록 | `ssot.md` |
| 3 | 공용 데이터 레이어, 스키마, API, API 키, 행 단위 권한 | 앱이 세 개를 넘고 스키마를 관리할 수 있음 | 스키마 설계자, API 키 관리자 | 스키마, 권한표, API 키 대장, API 문서 | 이 문서의 3단계 |
| 4 | 사람·서비스의 관계와 기관의 판단 기준을 구조화한 온톨로지 | 사례회의에서 판단 기준을 합의하고 지속적으로 수정함 | 사례회의와 데이터 관리자 | 체계, 데이터, 기준, 기준 개정 이력 | 이 문서의 4단계 |

## 0단계: 종이와 엑셀을 개별 관리

0단계를 유지하는 것도 가능한 결정입니다. `../assess/form-audit.md`로 양식을 점검한 뒤 반복 입력과 집계 때문에 앱 전환이 필요한 업무만 1단계로 이동합니다. 외부에서 형식을 정한 법정서식과 단순 결재 문서는 기존 문서 형식을 유지하는 편이 적절할 수 있습니다.

## 1단계: 반복 업무를 처리하는 앱 하나

담당자의 반복 업무 하나를 처리하는 소규모 앱을 만듭니다. 기능과 운영 범위를 작게 유지하고, 앱을 다시 만들거나 수정할 때 필요한 맥락을 문서로 남깁니다.

- `DECISION.md`에는 플랫폼과 데이터 구조를 선택한 이유를 기록합니다.
- `../requirements/requirements.md`에는 앱의 완료 조건을 기록합니다.
- `CLAUDE.md`와 `AGENTS.md`에는 AI가 따라야 할 구현 규칙을 기록합니다.
- `../../ops/handover.md`에는 계정, 배포, 백업, 장애 대응 절차를 기록합니다.

앱이 두 개 이상인데 각 앱이 별도의 이용자 명부를 가지고 있다면 2단계를 검토합니다.

## 2단계: 이용자 명부와 ID를 단일 원본으로 관리

모든 데이터를 한 파일에 넣는 것이 아니라 모든 앱과 파일이 같은 이용자 ID 체계를 사용하도록 만듭니다. 이용자 명부를 하나의 원본으로 정하고 새 앱은 이용자를 별도로 등록하지 않고 이 명부를 참조합니다. 구체적인 구현 방법은 `ssot.md`에서 설명합니다.

이 단계에는 새 이용자를 등록하고 중복을 통합하며 ID 규칙을 관리하는 **명부 관리자** 역할이 필요합니다. 인수인계의 중심도 개별 앱에서 이용자 명부와 ID 체계로 이동합니다. 앱을 중단하거나 다시 만들더라도 공용 원본 데이터는 유지되어야 합니다.

## 3단계: 기관 공용 데이터 레이어와 API

기관이 공통으로 사용할 테이블과 스키마를 설계하고 API를 제공합니다. 앱과 사용자마다 별도의 API 키를 발급하고 필요한 데이터에만 접근할 수 있도록 권한을 제한합니다. 각 담당자는 업무에 맞는 화면을 만들 수 있지만 모든 앱은 같은 원본 데이터를 사용합니다.

공용 데이터 레이어를 MCP로 AI와 연결하면 사용자는 일반적인 문장으로 집계를 요청할 수 있습니다. 일부 업무에서는 별도의 조회 화면을 만들 필요가 줄어들 수 있습니다. 다만 MCP에는 개인정보가 없는 집계 뷰를 기본으로 연결하고 S등급 데이터의 전송은 계약, 동의, 처리방침을 확인한 뒤 결정합니다.

3단계에서는 다음 규칙을 적용합니다.

1. **공용 데이터 레이어 전체를 검증되지 않은 자체 코드로 만들지 않습니다.** 특정 담당자가 만든 API 서버 하나에 기관의 모든 앱이 의존하면 담당자 퇴사와 서버 장애가 기관 전체에 영향을 줍니다. API, 인증, API 키, 행 단위 권한을 지원하는 검증된 제품을 사용하고 기관은 스키마, 권한 규칙, 운영 문서를 관리합니다.
2. **API 키 발급과 폐기를 공식 업무로 지정합니다.** 발급 대상, 권한 범위, 발급일, 폐기일을 API 키 대장에 기록합니다. 퇴사와 업무 변경 시 권한을 회수하는 담당자와 처리 기한도 정합니다.
3. **쓰기 권한과 조회 범위를 최소화합니다.** 데이터 변경은 정해진 API를 통하고 서버에서 사용자 권한과 입력값을 검증합니다. 개별 앱이 공용 스키마를 임의로 변경하거나 별도의 기준 데이터를 만들지 못하게 합니다.

인수인계 자료에는 테이블과 컬럼의 의미를 설명한 스키마 문서, 역할별 읽기·쓰기 권한표, API 키 대장, API 문서를 포함합니다. 스키마 문서에는 테이블 관계 그림을 Mermaid로 넣어 저장소에서 바로 보이게 하고, 경로 A는 Supabase 대시보드의 Schema Visualizer로도 확인합니다. 개발을 모르는 후임자와 사례회의가 데이터 구조를 그림으로 볼 수 있어야 합니다. 이 자료가 최신 상태라면 후임자는 기존 앱의 모든 코드를 이해하지 못해도 같은 데이터를 사용하는 새 앱을 만들 수 있습니다.

희망이음 같은 외부 법정 시스템이 API를 제공하지 않으면 기관 앱과 외부 시스템에 같은 내용을 다시 입력하는 문제는 남습니다. 3단계는 기관 내부 데이터의 중복을 줄이는 단계이며 연결 기능이 없는 외부 시스템까지 자동화할 수는 없습니다.

## 4단계: 관계와 판단 기준을 데이터로 관리

온톨로지는 기관에서 사용하는 개념, 관계, 판단 기준을 사람과 컴퓨터가 함께 해석할 수 있는 구조로 명시한 것입니다. 특정 데이터베이스 제품을 의미하지 않으며 기관 구성원이 업무 개념과 기준에 합의하는 과정이 핵심입니다.

온톨로지에 담는 것은 기관이 스스로에게 한 약속과 당사자가 스스로 말한 것입니다. 실인원을 누구로 세는지, 며칠 안 보이면 찾아가는지는 기관의 약속이고, 생태도의 관계와 당사자가 정한 목표는 당사자의 말입니다. 실천가가 당사자에 대해 판단한 것은 서술 기록에 남기고 구조화하지 않습니다. 온톨로지가 아는 것은 그 사람이 아니라 언제 만나러 갈지이고, 만난 뒤의 일은 사람의 몫입니다. 사람을 상태를 가진 객체로 모델링해 조치를 자동으로 내보내는 기업용 온톨로지와는 방향이 반대입니다. 강점관점, 해결중심, 당사자 관점의 실천에서는 기록의 대부분이 서술과 예외로 남고 구조화되는 부분이 작은 것이 정상입니다.

| 구성 요소 | 정의 | 앞 단계와의 관계 |
|---|---|---|
| 체계(Schema) | 개념의 분류와 위계 | 3단계의 스키마를 확장 |
| 데이터(Data) | 개체, 관계, 속성으로 표현한 사실 | 2단계의 단일 원본을 확장 |
| 기준(Rule) | 특정 상황에서 기관이 확인하거나 조치하기로 합의한 조건 | 4단계에서 추가 |

관계 데이터는 개체, 관계, 속성으로 나눕니다. 개체는 사람·서비스·장소처럼 구별할 수 있는 대상이고, 관계는 두 개체의 연결을 나타냅니다. 속성은 주소·건강 상태 같은 개체의 정보나 접촉 빈도·지원 방식 같은 관계의 정보입니다. 관계는 `주체–관계–객체`의 트리플로 표현할 수 있습니다.

```
서술 기록: 김OO 어르신은 무릎 통증으로 외출이 어려워 경로당 이용을 중단했고 도시락 서비스를 연계함
관계 데이터: 서비스이용(김OO, 도시락, 주 5회) / 이용중단(김OO, 경로당, 거동 불편)
```

관계 데이터가 있으면 특정 지원자가 더 이상 활동하지 못할 때 영향을 받는 이용자를 찾거나 비슷한 지원 공백이 있는 이용자를 함께 확인할 수 있습니다. 관계에 시작일과 종료일을 붙이면 종이 생태도가 보여 주지 못하는 변화도 볼 수 있습니다. 모든 언급을 관계로 만들 필요는 없습니다. 반복해서 등장하고 지속적인 관리가 필요한 관계만 구조화하고 일회성 맥락은 서술 기록에 남깁니다. 사람 사이의 관계를 데이터로 만들 때는 수집 목적과 범위를 당사자에게 알리고 필요한 동의를 확인합니다.

개체는 세 종류이고 규칙이 다릅니다.

- **조직·장소·프로그램·자원**: 경로당, 병원, 반찬가게, 기관의 프로그램. 누구의 지도에서든 연결하는 공유 개체입니다. 마을 자원 지도가 이것입니다.
- **기관과 관계를 맺고 등록된 사람**: 이용자, 자원봉사자, 후원자, 주민활동가, 강사. 각자의 명부에 동의를 받고 등록된 사람이므로 공유 개체가 됩니다. 사람 개체는 온톨로지에서 새로 만들지 않고 해당 명부의 ID를 참조합니다(`ssot.md`). 한 사람이 두 명부에 있을 때 둘을 잇는 것은 목적과 동의를 확인한 뒤 기관이 결정합니다.
- **이용자가 말한 사적 관계인**: 이웃, 친구, 연락하지 않는 가족. 기관과 관계가 없고 동의도 없으므로 그 이용자의 지도 안에서만 존재하고 다른 이용자의 지도와 합치지 않습니다. 종이 생태도에도 같은 사람이 나오지만, 데이터에서 합치면 그 사람이 동의 없이 여러 이용자를 잇는 개체가 됩니다.

관계도 두 종류이고 출처를 함께 저장합니다. 기관이 맺어 준 관계(자원봉사자 매칭, 프로그램 참여, 도시락 배달)는 기관의 기록이고 공유 개체 사이를 잇습니다. 당사자가 말한 관계(옆집이 챙겨 준다)는 진술이고 그 이용자의 지도 안에 남습니다. 말한 사람이 우연히 기관의 자원봉사자라도 기관이 매칭한 것이 아니면 자동으로 잇지 않습니다. 당사자의 말은 원문으로 저장하고 기관의 분류는 옆에 둡니다.

생태도는 자료가 아니라 당사자와 함께 그리는 행위입니다. 관계 데이터는 생태도를 대신하는 것이 아니라 생태도의 저장소이고, 화면에서 다시 생태도로 그려져 당사자가 보면서 고칠 수 있어야 합니다. 실천가가 혼자 채우는 데이터베이스가 되면 당사자 관점이 빠집니다. 마을 주민의 관계망을 그리려면 참여 사업으로 동의를 받고 주민이 자기 자리와 자원을 스스로 등록하는 방법만 있습니다. 그때 주민은 사례의 대상이 아니라 당사자입니다. 사례관리 기록에서 뽑은 이웃 정보로 마을 관계망을 만드는 것은 목적을 벗어난 결합이고 하지 않습니다.

어떤 것을 기준으로 올릴지는 다음 규칙으로 정합니다.

- **올리는 것**: 사람마다 다르게 세는 데이터의 정의와 확인 조건. 실인원을 누구로 세는지, 종결이 언제인지, 참여 1회가 무엇인지, 이 서비스가 어느 프로그램에 속하는지, 며칠 안 보이면 찾아가는지. 담당자마다 다르게 세면 보고가 틀리고, 하나로 정해도 당사자에게 해가 없습니다.
- **올리지 않는 것**: 사람의 상태에 대한 판정. 위기 정도, 욕구, 협조 여부, 강점. 사회복지사마다 다르게 보는 것이 정상이고 그것이 전문적 판단입니다. 구성원 간 판단이 다르다는 이유로 하나의 기계 정의로 고정하지 않고 사례회의에서 논의합니다. 올리더라도 "위기다"라는 판정이 아니라 "확인한다"는 조건의 형태로만 올립니다.
- **자동 조건에 넣지 않는 것**: 당사자가 매긴 척도 점수. 척도는 당사자와의 대화를 위한 숫자이고, 몇 점 이하면 개입한다는 식으로 쓰면 감시 도구가 됩니다. 조건은 출석, 수령, 방문, 진술된 관계의 유무처럼 기록된 사실로만 만듭니다.

기관의 판단 기준은 다음과 같이 조건과 조치로 표현합니다.

- 이웃 돌봄 관계가 0명이면 돌봄 공백 여부 확인
- 경로당이나 프로그램에 5일 연속 참여하지 않으면 안부 확인
- 도시락을 5일 연속 비대면으로 수령하면 안부 확인

이 값은 법정 기준이 아니라 기관이 사례회의에서 합의한 예시입니다. 실제 기준은 이용자, 지역 환경, 실천 경험에 따라 달라지므로 기관이 근거와 개정 이력을 관리해야 합니다.

기준을 적용한 뒤에는 결과와 당사자의 의견을 확인하고 사례회의에서 기준을 수정합니다. 확인 조건이 울려 찾아갔으면 그 결과를 기록하는 칸을 둡니다. 방문했는지, 만났는지, 무엇을 연계했는지, 당사자가 무엇이라고 했는지. 이것은 기관의 행위 기록이라 구조화해도 되는 쪽이고, 사례회의가 "이 기준은 열 번 울려 아홉 번 아무 일도 없었다"를 보고 기준을 고칠 근거가 됩니다. 기록이 없으면 기준 수정은 인상으로만 이루어집니다. 이 되먹임은 사례회의에서 닫히고, 시스템이 결과를 보고 스스로 기준을 조정하지 않습니다. 이 과정에서 다음 원칙을 지킵니다.

- 수정 대상은 사람의 점수가 아니라 기관이 정한 조건과 기준입니다.
- AI는 검토할 사례를 제안할 수 있지만 사회복지사가 기록과 상황을 확인하고 당사자와 함께 판단합니다.
- 분석 결과만으로 서비스 자격이나 지원 여부를 자동 결정하지 않습니다. 자동화된 결정이나 고영향 AI에 해당하는지 별도 검토합니다.

관계 데이터의 목적은 이용자의 관계와 생활 변화를 이해하는 것입니다. CCTV, 출입 기록, 결제 기록, 통화 기록처럼 기술적으로 수집 가능한 데이터를 당사자와의 합의 없이 결합하지 않습니다. 같은 `경로당 이용 중단`도 건강 문제, 관계 갈등, 당사자의 선택에 따라 의미가 다르므로 관계 변화를 해석하기 전에 당사자에게 맥락을 확인합니다. 이 단계에서도 `../assess/ethics.md`의 다섯 질문을 다시 적용합니다.

저장 방식은 조회 요구에 따라 선택합니다. 초기에는 관계형 데이터베이스에 시작일과 종료일이 있는 트리플 테이블 하나를 만들어 시작할 수 있고, AI도 그대로 읽습니다. 담당자 한 명의 사례가 수십 건인 기관에는 이것으로 충분합니다. 여러 단계의 관계를 자주 탐색해야 할 때만 Neo4j나 TypeDB 같은 그래프 데이터베이스를 검토합니다.

기관의 판단 기준은 파일이 아니라 시트나 테이블의 행으로 관리합니다. 열은 기준 번호, 조건, 조치, 시행일, 종료일, 결정한 회의, 이유입니다. 기준을 바꿀 때는 행을 고치지 않고 종료일을 적은 뒤 새 행을 추가하고, 앱은 시행 중인 행만 읽습니다. 경로 C면 구글 시트, 경로 A면 테이블입니다. 사례회의에서 정하면 담당자가 행 하나를 추가하고 개발자나 배포 없이 그날부터 반영됩니다. 몇 달 뒤 어느 이용자가 왜 확인 대상이었는지 물으면 그때 시행 중이던 행을 보면 됩니다. 이 시트나 테이블이 곧 기준 개정 이력이고, `record-integrity.md`의 보관 등급 1을 적용합니다. AI가 산출물을 만들 때 적용한 기준 번호를 함께 남기면 기준이 바뀐 뒤 영향받은 산출물을 찾을 수 있습니다.

AI가 참조할 이용자별 요약이나 페이지를 만든다면 두 번째 기록으로 쌓지 않고 원본 위의 뷰로 만듭니다. 관계 데이터, 서비스 기록, 당사자의 목표와 척도 원문, 최근 서술 기록에서 매번 다시 생성하고, 모든 문장에 출처 기록과 날짜를 붙이고, 담당자 판단 근거 칸은 사람만 씁니다. 요약을 다시 요약하며 누적하면 한 번 들어간 표현이 이후 모든 산출물에 물려지고, 원본을 파기해도 남습니다. 원본에서 생성하면 `../requirements/ai.md`의 원본 보존과 근거 표시 규칙이 지켜지고, 원본을 파기하면 함께 사라지며, 당사자에게 보여 주고 고칠 수 있는 페이지가 됩니다.

온톨로지는 여러 기관이 공유할 수 있는 법·제도의 상위 체계와 기관이 직접 관리하는 판단 기준으로 구분할 수 있습니다.

| 구분 | 예시 | 관리 주체 |
|---|---|---|
| 법·제도의 상위 체계 | 위기상황을 인적 변동, 건강, 폭력, 경제, 환경 사건으로 분류 | 여러 기관이 공동으로 관리할 수 있는 공개 자산 |
| 기관 판단 기준 | 이웃 돌봄 관계가 없으면 돌봄 공백 여부를 확인 | 기관이 사례회의를 통해 관리하는 내부 자산 |

4단계에는 새로운 데이터베이스보다 사례회의에서 기준을 설명하고 합의하며 수정할 수 있는 운영 체계가 먼저 필요합니다. 인수인계 자료에는 체계, 데이터, 기준 시트나 테이블의 위치와 수정 권한자를 포함합니다. 기준의 행이 시행일, 종료일, 이유, 결정한 회의를 담고 있으므로 별도의 개정 대장은 필요하지 않습니다.
