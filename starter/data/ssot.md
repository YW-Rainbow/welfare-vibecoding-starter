# 이용자 데이터를 단일 원본으로 관리하는 방법

> 출처·최신판: https://github.com/YW-Rainbow/welfare-vibecoding-starter
> 무엇을 만들지는 `../assess/form-audit.md`, 어느 플랫폼에서 만들지는 `../workflow.md`를 보고 정합니다. 이 문서는 여러 앱과 파일이 어떤 데이터를 원본으로 쓸지 정할 때 봅니다. 앱을 두 개 이상 만들 계획이라면 먼저 확인하세요.

## 중복 입력과 수작업 취합의 문제

프로그램 접수는 전화와 종이로 받아 엑셀에 적고, 출석은 인쇄한 출석부에 강사가 표시하고, 담당자가 합계만 엑셀로 옮기고, 팀과 기관이 취합해 시군구에 제출하고, 시군구는 다시 상위 기관에 올립니다. 단계마다 사람이 옮겨 적고, 중간에 한 번 틀리면 그 아래 작업을 전부 다시 합니다. 모든 결과물이 최초 기록에서 나오는데, 이 구조에서는 최초 기록을 참조하지 않고 사본에서 다시 사본을 만듭니다. 디지털 전환은 종이를 화면으로 바꾸는 일이 아니라, 최초 기록이 생기는 순간 제대로 모으고 그 뒤의 모든 작업이 이 기록을 참조하게 만드는 일입니다. 엑셀에 옮겨 적는 것은 디지털이 아니라 옮겨 적기입니다. 기관 안에서는 옮겨 적기를 참조로 바꾸고, 기관 밖으로 나가는 보고서는 최초 기록에서 만듭니다(`../requirements/hwp.md`).

최초 기록을 제대로 모으려면 두 조건을 갖춰야 합니다. 기록이 생기는 순간 그 일을 아는 사람이 입력해야 하고, 기록에 이용자 ID가 붙어야 합니다. 강사가 종이에 표시하고 담당자가 나중에 입력하면 첫 단계부터 옮겨 적기가 됩니다.

종이 출석부의 내용을 시트에 입력하고 다시 실적표로 복사하면 단계마다 누락과 오입력이 생깁니다. 담당자마다 파일을 따로 쓰면 같은 이용자의 이름과 정보가 파일마다 다르게 적혀 실인원을 계산할 때 사람이 직접 대조해야 합니다. 이 문제는 담당자가 주의하지 않아서라기보다 같은 정보를 여러 곳에 입력하게 만든 구조 때문에 생깁니다.

목표는 취합을 더 빠르게 하는 것이 아니라 **같은 사실을 한 번만 입력하고 다른 기록이 그 원본을 참조하게 만드는 것**입니다. 이를 SSoT(Single Source of Truth, 단일 원본)라고 합니다.

## 두 가지 기본 규칙

1. **이용자는 이용자 명부에서만 등록합니다.** 개별 앱과 업무 시트에서 이용자 정보를 따로 만들지 않습니다.
2. **모든 기록은 이용자 ID로 연결합니다.** 이름을 반복 입력하지 않고 이용자 명부의 고정된 ID를 참조합니다.

이 두 규칙을 지키지 않으면 앱이 늘어날수록 중복 데이터와 수작업 대조 비용도 함께 늘어납니다.

## 공통 항목과 업무 단계를 연결합니다

단일 원본은 이용자 명부뿐 아니라 여러 업무가 함께 쓰는 데이터 항목의 정의에도 적용할 수 있습니다. 기관은 항목의 고유한 키, 사람이 읽는 이름, 의미, 값의 형식과 관리 주체를 공통 목록에서 한 번 정의하고, 각 업무 단계와 화면은 필요한 항목을 참조합니다. 화면마다 같은 뜻의 항목을 새로 만들면 이름과 형식이 조금씩 달라져 다시 수작업으로 맞춰야 합니다.

업무 단계를 설계할 때는 공통 항목 목록과 대조해 다음 상태를 확인합니다.

- 어느 단계에서 만들고 다른 단계가 이어서 사용하는 항목
- 현장에는 필요하지만 공통 목록에 아직 없는 항목
- 공통 목록에는 있지만 실제 업무에서 사용되지 않는 항목

새 항목은 필요한 단계와 사용 목적을 확인한 뒤 공통 목록에 추가합니다. 사용되지 않는 항목도 곧바로 삭제하지 않고, 법적 근거가 있는지, 보고나 연계 업무에 쓰이는지, 기존 데이터를 보존해야 하는지 확인합니다. 화면의 배치와 입력 순서는 담당 업무에 맞게 바꿀 수 있지만, 같은 의미의 데이터가 서로 다른 원본으로 갈라지게 해서는 안 됩니다. 전체 양식을 업무 단계와 함께 점검하는 방법은 `../assess/form-audit.md`에 있습니다.

## 사회복지기관의 기준 데이터는 이용자입니다

일반적인 기업 시스템은 직원을 중심으로 데이터를 구성하기도 하지만 사회복지기관에서는 이용자를 기준으로 참여, 상담, 후원, 사례관리 기록을 연결해야 합니다. 그래야 이용자별 장기 변화와 재이용 현황을 확인하고 실적의 실인원을 정확하게 계산할 수 있습니다.

## 권장 데이터 구조

```
[기준 데이터]
이용자 명부       이용자 ID를 발급하는 유일한 원본
프로그램 목록     프로그램 ID, 사업 구분, 유형, 목표 인원
프로그램 회차     프로그램 ID + 회차 ID, 일시, 장소, 강사, 주제

[업무 기록]
사업·팀별 기록    참석한 이용자를 한 행씩 기록하고 이름·성별·일시는 반복 저장하지 않음

[집계]
총괄 실적         업무 기록을 자동으로 집계하고 마지막 단계에서 명부와 조인함
```

총괄 실적에는 담당자가 값을 직접 입력하지 않습니다. 업무 기록에서 자동으로 가져와 집계해야 복사하면서 생기는 누락과 불일치를 막을 수 있습니다.

## 참여 기록의 기본 컬럼

| 컬럼 | 의미 | 다른 테이블과 연결해 확인할 정보 |
|---|---|---|
| 기록 ID | 한 행의 고유 식별자 | 입력자, 입력 시각, 메모 |
| 프로그램 ID | 참여한 사업 | 사업 구분, 유형, 목표 인원 |
| 회차 ID | 프로그램의 특정 회차 | 일시, 장소, 강사, 주제 |
| 이용자 ID | 참여한 이용자 | 성별, 생년월일, 해당 연도의 연령 |
| 취소 여부 | 잘못 입력하거나 취소된 기록인지 표시 | 해당 없음 |

참여 기록에는 이름, 성별, 회차 일시를 반복해서 저장하지 않습니다. ID로 필요한 정보만 조회하면 중복 수정과 표기 불일치를 줄이고 파일별 접근 범위도 나눌 수 있습니다.

연령대는 해마다 달라지므로 기록에 `60대`처럼 고정해서 저장하지 않습니다. 이용자 명부에는 생년월일을 저장하고 보고서의 기준 연도에 따라 연령대를 계산합니다. 성별처럼 이용자 기준 데이터도 명부에서 관리합니다.

### 결석과 취소를 구분합니다

참여 실적은 보통 참석한 사람만 한 행씩 기록합니다. 결석자 행까지 회차마다 만들면 데이터 양이 늘고 실제 참여 건수를 계산할 때 매번 제외해야 합니다. 출석률이 필요한 프로그램만 등록자 명단을 따로 두고 참석 기록과 비교해 계산합니다.

취소는 결석과 다릅니다. 잘못 입력하거나 중복 입력한 행을 삭제하면 수치가 바뀐 이유를 알 수 없습니다. 기존 행에 취소 여부와 취소 사유를 기록하고 집계에서는 취소되지 않은 행만 사용합니다. 증거로 사용하는 기록에는 `record-integrity.md`의 변경 이력 기준을 추가로 적용합니다.

### 행 번호를 ID로 사용하지 않습니다

Google Sheets의 행 번호는 행을 삭제하거나 정렬하면 바뀌므로 식별자로 사용할 수 없습니다. 저장할 때 UUID처럼 바뀌지 않는 기록 ID를 만듭니다. 시트 수식으로 ID를 만들었다면 결과를 값으로 고정해야 행을 옮기거나 정렬한 뒤에도 ID가 유지됩니다.

프로그램 ID와 회차 ID도 한 문자열로 합치지 않고 별도 컬럼으로 저장합니다. 예를 들어 `2026-어르신교실-03`을 한 칸에 저장하면 프로그램만 집계할 때 문자열을 다시 분리해야 하고 표기 오류도 생기기 쉽습니다. 두 컬럼으로 나누면 각각 유효성 검사를 적용하고 프로그램별로 바로 집계할 수 있습니다.

## Google Sheets로 구현하는 경우

Google Sheets를 선택했다면 개인정보를 다른 플랫폼에 중복 저장하지 않고 되도록 Google Workspace 안에서 모두 구성합니다. 플랫폼이 늘면 개인정보 처리 수탁자와 계정·백업·인수인계 범위도 늘어납니다. Google Sheets는 행 단위 권한을 제공하지 않으므로 접근 권한이 다른 데이터는 파일을 분리합니다.

```
① 이용자 명부       전 직원 조회 / 명부 담당자만 수정
② 참여·출결 기록    프로그램 담당자 수정
③ 사례관리 기록     담당자와 슈퍼바이저만 접근
④ 총괄 실적         ①과 ②를 자동 집계 / 직접 입력 금지
```

③ 사례관리 파일에서 ④ 총괄 실적으로는 상담 내용이 아니라 집계 결과만 전달합니다. 사례관리 파일 전체를 `IMPORTRANGE`로 가져오면 접근 권한을 파일별로 분리한 의미가 없어집니다. ③ 안에 집계 탭을 따로 만들고 필요한 숫자 범위만 ④에서 가져옵니다.

```
③ 사례관리  ├─ 기록 탭: 상담 내용, 외부 파일로 전달하지 않음
             └─ 월별 집계 탭: 건수와 실인원 등 집계값만 제공
                                      ↓ IMPORTRANGE 범위를 월별 집계로 제한
④ 총괄 실적
```

이용자와 프로그램 컬럼은 데이터 유효성 검사로 명부에 있는 값만 선택하게 합니다. 각 업무 파일에 명부를 `IMPORTRANGE`로 불러오는 숨김 탭을 만들고 그 범위를 선택 목록으로 사용하면 이름의 띄어쓰기와 표기 차이로 실인원이 달라지는 문제를 줄일 수 있습니다.

조인은 원본 행 전체가 아니라 집계가 끝난 결과에 적용합니다. 수만 행에 `VLOOKUP`을 반복하면 시트가 느려집니다.

```
업무 시트 ──IMPORTRANGE──→ 원본 모음 탭
                                  ↓ QUERY로 먼저 집계
                              집계 탭
                                  ↓ 이용자 명부 조인
                              최종 실적표
```

실인원은 집계 전에 중복된 이용자 ID를 없애야 하므로 실인원 집계 탭을 따로 두거나 `UNIQUE`·`QUERY`를 조합해 씁니다.

Google Sheets 구성에서는 다음 네 가지를 지킵니다.

1. 사례관리 파일은 링크 공유를 끄고 다운로드·복사·인쇄 권한도 필요한 범위로 제한합니다. 앱에서만 접근한다면 사람에게는 파일을 직접 공유하지 않습니다.
2. Google Sheets만으로는 필요한 접근 로그가 자동으로 남지 않습니다. 앱에서 조회·수정·삭제·출력할 때 로그를 따로 남기고 그 로그에 적용되는 보관 기간을 확인합니다.
3. `IMPORTRANGE`는 기준 데이터와 업무 기록에서 총괄 실적으로 이동하는 한 방향으로만 사용합니다. 총괄 실적의 값을 원본에 다시 쓰지 않습니다.
4. 총괄 실적에는 직접 입력하지 않습니다. 집계 결과가 잘못되었다면 기준 데이터나 업무 기록을 수정합니다.

## 기존 데이터 이관

기존 시트와 문서의 데이터를 새 명부와 연결할 때는 빠지는 기록이나 다른 이용자에게 잘못 붙는 기록이 없도록 다음 순서를 따릅니다.

1. **원본 보존**: 기존 파일을 삭제하거나 덮어쓰지 않고 읽기 전용으로 보관합니다.
2. **형식 통일**: 컬럼 이름, 날짜, 전화번호, 코드 등 값의 형식을 표준 구조에 맞춥니다.
3. **대응표 작성**: 기존 행의 식별 정보와 새 이용자 ID를 연결한 표를 남깁니다.

이관을 실행하기 전에 백업, dry-run, 표본 대조, 관리자 승인을 거칩니다. dry-run은 새 원본에 쓰지 않고 변환 결과와 오류 목록만 만드는 시험 실행입니다. 이관 코드는 가상 데이터로 스테이징에서 먼저 돌립니다. 실제 파일은 AI 작업 환경에 올리지 않고 운영 DB나 운영 스크립트에서 실행되는 이관 함수(GAS 함수, DB 함수 등)가 읽게 합니다. AI가 받는 결과는 전체 건수와 오류 유형별 건수뿐이고, 오류 행 목록과 표본 대조는 담당자가 봅니다(`../rules/agentic.md`). 오래 쌓인 기록은 일부만 빠져도 다시 만들기 어렵습니다. 기능을 빨리 만드는 것보다 이관한 데이터가 정확하고 복구할 수 있는지를 먼저 확인합니다.

### 문제가 있는 행은 삭제하지 않고 품질 등급을 기록합니다

ID 누락, 중복, 잘못된 날짜처럼 문제가 있는 행을 이관하면서 자동으로 삭제하지 않습니다. 다음 품질 등급을 함께 저장하고 C와 D는 담당자가 확인합니다.

| 등급 | 기준 | 사용 방법 |
|---|---|---|
| A | 검증 결과 문제 없음 | 그대로 사용 |
| B | 표기 불일치 등 경미한 문제 | 사용 가능, 이후 정리 |
| C | 범위를 벗어난 값이나 날짜 오류 등 확인 필요 | 담당자 확인 후 사용 |
| D | ID 없음, 중복, 상호 모순 등 신뢰하기 어려움 | 공식 보고서와 분석에서 제외하되 원본은 보존 |

D등급 행을 보존하면 나중에 원본과 다시 대조해 복구할 수 있고, 품질 문제가 얼마나 되는지도 알 수 있습니다. 공식 집계에서는 제외한 사유와 건수를 함께 기록합니다.

### 구조화된 값과 서술 기록을 함께 보존합니다

날짜, 횟수, 분류 같은 구조화된 컬럼은 집계에 필요하지만 그 수치가 나온 배경을 모두 설명하지는 못합니다. 기존 서술 기록은 삭제하지 않고 관련 행과 연결해 보존합니다. AI 분석을 도입하기 전에는 무엇을 어떤 기준으로 기록하는지 먼저 통일해야 합니다. 입력 기준이 제각각이면 AI가 만든 요약과 분류도 일관되게 검증할 수 없습니다.

## 담당자별 앱을 만드는 경우

담당자는 업무에 맞는 화면과 기능을 따로 만들 수 있습니다. 그러나 앱마다 이용자 명부와 별도 데이터베이스를 만들면 같은 사람이 서로 다른 ID로 등록되고, 담당자가 퇴사한 뒤 아무도 관리하지 않는 개인정보 저장소가 남을 수 있습니다.

공용 기준 데이터와 담당자 전용 데이터를 다음과 같이 분리합니다.

| 구분 | 데이터 | 저장 원칙 |
|---|---|---|
| 공용 원본 | 이용자 명부, 참여 기록, 프로그램·회차 목록 | 모든 앱이 같은 원본을 참조 |
| 담당자 전용 | 사례 메모, 개인 태그, 진행 단계, 다음 방문 예정 | 별도 테이블이나 시트에 저장하되 이용자 ID로 연결하고 담당자에게만 접근 허용 |

담당자는 화면과 전용 항목을 업무에 맞게 구성할 수 있지만 이용자는 새로 등록하지 않고 공용 명부에서 선택합니다. 이렇게 하면 담당자는 업무 자율성을 유지하고, 기관은 실적을 집계하고 인수인계할 수 있습니다.

## API와 MCP 접근 권한

여러 앱이 같은 원본을 사용하면 일관성을 높일 수 있지만 공용 원본의 권한을 잘못 설정했을 때 영향을 받는 범위도 커집니다.

- 앱마다 필요한 테이블과 행만 허용합니다. RLS는 deny-by-default로 설정하고 모든 직원에게 전체 데이터 접근 권한을 주지 않습니다.
- MCP는 개인정보가 없는 집계 뷰를 기본으로 연결합니다. MCP가 이용자 데이터베이스를 직접 조회하면 실제 개인정보가 AI 서비스로 전송될 수 있습니다. 개인별 상담 이력을 제공하기 전에 `../requirements/masking.md`의 계약·동의·처리방침 조건을 확인합니다.
- 쓰기 API는 서버에서 입력값과 사용자 권한을 검증하고 변경 이력을 기록합니다. 앱이 임의로 기준 데이터의 컬럼이나 ID를 만들지 못하게 합니다.

## 도입 범위

처음부터 기관의 모든 시스템을 통합할 필요는 없습니다. 먼저 이용자 명부 하나를 원본으로 정하고, 다음에 만드는 앱이 그 명부의 이용자 ID를 참조하게 합니다. 그다음 프로그램 목록과 회차 목록처럼 여러 업무가 함께 쓰는 데이터를 하나씩 더합니다.

단일 원본은 모든 데이터를 한 파일에 저장한다는 뜻이 아닙니다. 접근 권한에 따라 파일과 테이블을 나누더라도 모든 앱이 같은 ID 체계와 기준 데이터를 사용하면 됩니다.

이 문서는 `levels.md`의 2단계에 해당합니다. 앱이 세 개 이상이고 스키마와 접근 권한을 관리할 담당자가 있다면 공용 데이터 레이어와 API를 운영하는 3단계를 검토합니다. 관계와 기관의 판단 기준까지 데이터로 관리하려면 4단계를 검토합니다. 지금 문제가 명부 중복뿐이라면 2단계를 유지하면 됩니다.
