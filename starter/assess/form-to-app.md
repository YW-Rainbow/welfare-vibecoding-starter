# HWP 양식에서 앱까지: 양식을 판정 자료로 쓰는 절차

> 출처·최신판: https://github.com/YW-Rainbow/welfare-vibecoding-starter
> 사용자가 HWP 양식 파일을 주면서 "이걸 앱으로 만들어 달라"고 할 때 AI가 따르는 순서입니다. 양식 파일은 `../requirements/hwp.md`의 rhwp MCP로 읽습니다.

## 이 문서를 적용하는 시점

- 사용자가 HWP나 HWPX 양식 파일을 주며 입력하고 출력하고 통계를 내는 앱을 만들자고 할 때
- 기존 양식의 칸을 데이터 항목으로 바꾸려 할 때

양식이 여럿이면 `form-audit.md`로 전체 양식을 먼저 점검하고, 앱으로 전환하기로 한 양식만 이 절차로 넘어옵니다.

## 원칙: 양식은 앱의 명세가 아니라 단서입니다

양식의 칸을 그대로 데이터베이스 컬럼으로, 양식 한 장을 앱 하나로 옮기면 없애거나 줄였어야 할 절차를 그대로 자동화하게 됩니다. `../workflow.md`에서 가장 경계하는 일입니다. 이유는 세 가지입니다.

- 양식의 칸 가운데 일부는 법령이나 지침의 근거가 없는 관행이고, 일부는 이용자 명부에 이미 있는 값을 다시 적는 칸입니다. 그대로 옮기면 없앨 절차가 코드에 고정됩니다.
- 양식에는 이용자 ID가 없고 이름과 생년월일만 있습니다. 실인원과 연인원 같은 통계는 ID 없이 나오지 않습니다. 그래서 양식을 데이터로 바꾸는 일은 반드시 이용자 명부(`../data/ssot.md`)와 연결하는 단계를 거칩니다.
- 기관에는 양식이 수십 개 있습니다. 양식마다 앱을 만들면 `../data/levels.md`의 1단계 앱이 수십 개 생기고 데이터가 흩어집니다. 이 절차의 단위는 양식 하나가 아니라 "양식 묶음 → 공용 데이터 모델 → 양식별 입력·출력 화면"입니다.

양식은 그 업무에 어떤 데이터가 오가는지 알려 주는 단서입니다. 앱의 모양은 판정을 거쳐 정합니다.

## 절차

### 1. 자료를 받습니다

- 빈 HWP 양식 파일. 채워진 문서는 받지 않습니다. 이용자와 직원의 개인정보가 들어 있습니다(`../rules/agentic.md`).
- 기관 이용자 명부의 항목 목록. 명부가 없다면 이 앱을 만들면서 명부를 단일 원본으로 함께 만들지 먼저 정합니다.
- 연말 실적 보고 항목. 실인원, 연인원, 프로그램·성별·연령대별 집계가 필요한지 확인합니다.

### 2. 양식을 읽습니다

rhwp MCP로 다음을 뽑습니다. 설정은 `../requirements/hwp.md`에 있습니다.

- `hwp_info`: 쪽수, 표 수, 누름틀 유무
- `hwp_fields`: 이미 있는 누름틀 이름
- `hwp_search`, 표 셀 조회: 각 칸의 라벨과 위치, 반복되는 행(참석자 명단, 회기별 기록)
- `hwp_export_svg`: 페이지 모양. 결재란, 서명란, 직인 자리, 인쇄 방향을 확인합니다

### 3. 칸을 분류합니다

양식의 모든 칸을 다음 다섯 가지로 나눈 표를 만듭니다. 이 표가 이 절차의 핵심 산출물이고 `DECISION.md`에 붙입니다.

| 분류 | 뜻 | 처리 |
|---|---|---|
| 명부 참조 | 이용자 이름, 생년월일, 연락처, 장애 유형처럼 이용자 명부에 있는 값 | 앱에 다시 입력하지 않고 이용자 ID로 연결해 표시만 합니다 |
| 양식 고유 | 이 업무에서 새로 생기는 값. 회기 날짜, 참석 여부, 활동 내용 | 앱의 데이터 항목이 됩니다 |
| 계산값 | 합계, 인원수, 출석률처럼 다른 값에서 나오는 값 | 저장하지 않고 조회할 때 계산합니다 |
| 근거 없음 후보 | 법령, 지침, 실제 독자를 찾지 못한 칸 | `form-audit.md`의 판정으로 없애거나 줄일지 사용자와 결정합니다 |
| 결재·서명 | 결재란, 서명란, 직인, 작성자 확인 | 데이터가 아니라 출력할 때 채우는 칸입니다. 결재 자체가 필요하면 `../data/record-integrity.md`를 적용합니다 |

분류 결과를 사용자에게 보여 주고 확인을 받습니다. 이때 각 항목의 이름도 함께 정합니다. 양식의 칸 이름을 그대로 쓰지 않고 `../requirements/design.md`의 "부르는 말과 이름" 기준으로 짓습니다. 이름은 화면, 출력물, 통계에 그대로 드러나고 나중에 바꾸기 어렵습니다. "스무 칸 가운데 일곱 칸은 근거를 찾지 못했고, 세 칸은 명부에서 가져옵니다"처럼 숫자로 말합니다.

### 4. 데이터 모델을 만듭니다

세 층으로 나눕니다.

- 이용자: 명부. 이용자 ID가 원본입니다.
- 프로그램과 회기: 반복되는 단위. 프로그램, 회기, 방문, 상담 등 업무에 맞는 이름을 씁니다.
- 기록: 양식 고유 항목. 이용자 ID와 회기 ID로 연결합니다.

1단계에서 받은 실적 보고 항목이 이 모델에서 나오는지 확인합니다. 실인원은 중복을 뺀 이용자 ID 수, 연인원은 기록 수이고, 연령대는 보고서의 기준 연도에 따라 계산합니다. 나오지 않는 항목이 있으면 모델을 고칩니다. 집계 요건이 있으면 `../workflow.md`의 안내대로 SQL 계열을 우선 검토합니다.

### 5. 판정합니다

`../workflow.md`의 절차를 그대로 진행합니다. 데이터 등급(양식의 자유서술 칸에 건강, 장애, 가족 관계가 들어가면 S등급), 규모, 사용자, 사람에 관한 기록 여부, 플랫폼 경로를 정하고 `DECISION.md`에 기록합니다. 3단계의 칸 분류표를 부록으로 붙입니다.

### 6. 출력을 설계합니다

`../requirements/hwp.md`와 `../requirements/print.md`를 적용합니다.

- 원 양식에 누름틀을 넣습니다. 이름은 데이터 항목 이름과 같게 합니다. 누름틀이 이미 있으면 그 이름에 맞춥니다.
- 반복 행은 반복 필드나 표 셀 좌표로 채우는 방식을 정합니다. 한 쪽을 넘는 명단은 쪽 나눔을 확인합니다.
- 결재·서명 칸은 출력 시점에 채우거나 비워 둡니다.
- 법정서식은 형식을 바꾸지 않습니다.

### 7. 앱을 만듭니다

선택한 경로의 `../rules/` 파일과 `../rules/agentic.md`를 적용해 다음을 만듭니다.

- 입력 화면: 양식 고유 항목만. 명부 참조 항목은 이용자를 고르면 자동으로 채워집니다.
- 목록과 조회: 회기별, 이용자별
- 통계: 4단계에서 확인한 실적 항목
- HWP 출력: 6단계의 누름틀 서식에 데이터를 채워 다운로드 또는 Drive 저장
- 백업, 삭제 완결성, 접근 로그: `../requirements/requirements.md`

### 8. 검증합니다

- 손으로 채운 기존 양식 한 건을 가상의 인물로 바꿔 스테이징 앱에 입력합니다. 운영 앱에는 시험 기록을 넣지 않습니다(`../workflow.md`의 원칙 9).
- 출력한 HWP를 원본 양식과 나란히 놓고 `hwp_export_svg`로 모양을 비교합니다.
- 실적 수치를 사용자가 손으로 낸 값과 맞춰 봅니다.
- 없앤 칸 때문에 실제로 불편하지 않은지 한 달 뒤 확인하는 일정을 `../../ops/handover.md`에 적습니다.

## 하지 않는 것

- 양식의 칸을 그대로 컬럼으로 만들지 않습니다.
- 채워진 양식을 AI에게 주지 않습니다.
- 양식마다 앱을 만들지 않습니다. 같은 명부를 쓰는 화면으로 만듭니다.
- 결재란과 서명란을 데이터로 저장하지 않습니다.
- 생성한 HWP를 다시 읽어 데이터로 쓰지 않습니다.
