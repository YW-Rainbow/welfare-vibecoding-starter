# Cloudflare Pages + Supabase 서울 리전 개발 기준(경로 A)

> 출처·최신판: https://github.com/YW-Rainbow/welfare-vibecoding-starter
> 적용 대상: 개인정보를 다루는 앱 가운데 `../workflow.md`의 경로 A(Supabase Pro)와 경로 A-무료(Supabase Free)
> 기본 구성: Supabase 서울(`ap-northeast-2`) 리전. Free와 Pro는 백업, 서비스 중단, 용량과 운영 조건을 확인해 선택합니다.
> 기준일: 2026-09
> 이 문서는 `agentic.md`와 함께 적용합니다.

아래 구성은 개인정보 처리 사업자와 경로를 줄이기 위한 권장 기본값입니다. 다른 구성을 사용하려면 개인정보 처리 위치, 접근 권한, 로그, 백업과 파기에서 같은 요건을 지키는지 설명하고 검증합니다.

## 권장 아키텍처

```
브라우저 ── supabase-js ──→ Supabase 서울(DB·Auth·Storage)   ← 개인정보 처리
브라우저 ←── Cloudflare Pages(정적 파일 제공)                 ← 개인정보 없음
브라우저 ──→ Cloudflare Workers(공개 데이터·통계 API)         ← 개인정보 없음
```

- 기본 구성에서는 개인정보를 브라우저에서 Supabase로 직접 전송해 중간 처리자를 늘리지 않습니다. 업무 규칙상 서버가 필요하다면 실행 위치를 고정할 수 있는 서버를 사용하고 데이터 흐름을 문서화합니다.
- 서버 로직이 필요하면 Supabase Edge Functions를 사용하고 모든 호출에 서울 리전을 명시합니다: `supabase.functions.invoke('fn', { region: 'ap-northeast-2' })`.
- 호출 헤더를 설정하기 어려운 webhook에는 `?forceFunctionRegion=ap-northeast-2`를 사용합니다. 리전을 지정하지 않은 Edge Function에 개인정보를 전송하지 않습니다.

## RLS

1. 개인정보를 저장하는 모든 테이블에서 RLS를 활성화합니다.
2. 명시적으로 허용한 접근만 가능하도록 deny-by-default 원칙을 적용합니다.
3. 정책은 기관 소속과 담당 업무를 기준으로 작성합니다. 예를 들어 `auth.uid()`가 해당 행의 담당자이거나 같은 기관 소속일 때만 조회를 허용합니다.
4. `service_role` 키(새 이름 secret key)는 프론트엔드 코드와 공개 저장소에 넣지 않습니다. 브라우저에는 publishable key(예전 이름 anon key)만 사용하고 실제 접근 권한은 RLS가 검사합니다.
5. 테이블을 만들 때 RLS 정책과 권한 테스트를 함께 작성합니다. 다른 계정으로 권한이 없는 행을 조회했을 때 거부되는지 자동 테스트에 포함합니다.

## 파일 저장소

1. 사진과 파일을 base64로 변환해 데이터베이스에 저장하지 않습니다. Storage 버킷에 파일을 저장하고 데이터베이스에는 경로와 메타데이터만 기록합니다.
2. 버킷은 private으로 만들고 유효기간이 1시간 이내인 signed URL로만 조회합니다.
3. 별도 요구가 없다면 업로드 전에 브라우저에서 긴 변 1600px, WebP 품질 80으로 압축하고 320px 썸네일을 만드는 것을 기본값으로 삼습니다. 원본 보존, 인쇄 품질과 네트워크 환경에 따라 값을 바꿀 수 있습니다.
4. 파일 경로는 보관 기간이 끝난 파일을 범위별로 찾을 수 있게 정합니다. `{연도}/{프로그램ID}/{회기}/{uuid}.webp`는 한 가지 예시입니다.
5. Storage 정책에도 데이터베이스와 같은 기관·담당자 기준의 접근 권한을 적용합니다.

## 삭제 완결성

1. 데이터베이스 테이블은 FK와 `ON DELETE CASCADE`를 사용해 일지를 삭제할 때 첨부 파일의 메타데이터 같은 연결 기록도 처리되도록 설계합니다. 결재와 감사 이력처럼 보존해야 하는 기록에는 CASCADE를 적용하지 않습니다.
2. Storage 파일은 데이터베이스의 CASCADE로 삭제되지 않으므로 삭제 함수에서 명시적으로 제거합니다. 행 삭제 뒤 연결 파일이 남지 않는지 테스트합니다.
3. 개인정보 테이블에 `retention_until` 컬럼을 두고 `pg_cron`으로 보관 기간이 끝난 데이터를 정기적으로 파기합니다.
4. 동의 철회나 삭제 요청은 사용자 확인, 해당 정보주체의 행·파일·계정 처리, 파기 대장 기록까지 한 절차로 구현합니다. 법적 보존 의무가 있는 기록은 즉시 삭제 대상과 구분합니다.

## 접근 로그

- 개인정보의 조회·수정·삭제·출력을 `access_log` 테이블에 `[접속 일시, auth.uid(), 수행 업무, 대상 행 ID]` 형식으로 기록합니다.
- 브라우저에서 Supabase로 직접 요청하는 구조에서는 앱 테이블에 접속지 IP를 기록하기 어렵습니다. Supabase API 로그의 보관 범위와 한계를 확인하고 내부관리계획에 기록합니다.
- 데이터 조회는 접근 로그를 남기는 데이터베이스 함수 또는 이에 준하는 서버 로직으로 처리합니다. `access_log`에는 INSERT만 허용하고 UPDATE와 DELETE를 차단하며 관리자만 조회할 수 있도록 RLS를 적용합니다.
- 개인정보 원본의 보관 기간이 끝나도 접속기록의 법정 보관 기간이 남아 있으면 로그를 삭제하지 않습니다. 원본 데이터와 로그의 파기 주기를 분리합니다.
- 이상 조회를 확인하는 정기 점검 일정을 기관 캘린더에 등록합니다.

## 백업

- Supabase Pro의 자동 데이터베이스 백업이 활성화되어 있는지 확인합니다. 복구 테스트는 운영 프로젝트에 되돌리지 않고 '새 프로젝트로 복원'으로 복원 시험 전용 프로젝트를 만들어 합니다. 이 프로젝트는 스테이징과 다르고 AI에게 연결하지 않으며, 사람이 행 수와 파일 수를 확인한 뒤 지웁니다.
- 기본 데이터베이스 백업에는 Storage 파일이 포함되지 않으므로 버킷 복제나 별도 다운로드 등 파일 백업 절차를 마련하고 `../../ops/handover.md`에 기록합니다.

## 배포와 스테이징

화면(Pages)과 공개 API(Workers)는 `cf-only.md` 4절처럼 GitHub Actions 없이 자동 배포합니다. 운영 반영과 DB 변경의 원칙은 `agentic.md`의 "운영 반영과 DB 변경은 사람이 결정하고 AI가 실행합니다"를 따릅니다. 이 경로는 개인정보를 다루므로 다음을 더합니다.

- **스테이징 DB는 Supabase 프로젝트를 하나 더 만듭니다.** 가상 데이터만 넣고, 스테이징 화면은 스테이징 프로젝트의 주소와 publishable key를 씁니다. Pages의 미리보기(Preview) 변수에는 스테이징 값만 넣고 운영 값은 운영(Production) 변수에만 둡니다. 스테이징 프로젝트를 운영과 같은 Pro 조직에 두면 컴퓨트 비용이 월 약 $10 늘어납니다. 비용을 늘리지 않으려면 별도의 Free 조직에 만듭니다. 무료 프로젝트는 두 개까지이고 7일 동안 요청이 없으면 일시 중지되므로, 확인하기 전에 대시보드에서 다시 켭니다.
- **DB 변경은 `supabase/migrations`의 파일로 남깁니다.** 사람이 승인하면 AI가 스테이징, 운영 순서로 적용합니다.
- **AI에게는 Supabase 공식 MCP 서버(`https://mcp.supabase.com/mcp`)를 OAuth로 연결해 권한을 줍니다.** 개인 액세스 토큰이 필요 없고, `?project_ref=<id>`로 프로젝트 하나에만 연결합니다. 평소에 연결해 두는 것은 스테이징 프로젝트뿐입니다. 읽기 전용(`read_only=true`)은 쓰기만 막고 행 내용은 그대로 읽히므로, 운영 프로젝트에는 읽기 전용으로도 늘 연결해 두지 않습니다. 운영 연결은 영향받는 행 수를 세거나 승인한 변경을 적용할 때만 켜고 끝나면 끕니다. `execute_sql`, `apply_migration`, `deploy_edge_function`은 확인 규칙에 넣어, 사람이 SQL이 `COUNT`나 마이그레이션 파일과 같은지 보고 승인합니다.
- **Edge Functions 배포도 운영 반영입니다.** 스테이징 프로젝트에 먼저 올리고, 운영에는 MCP의 `deploy_edge_function`을 승인해 올립니다. `supabase db push`, `supabase db dump`, `supabase functions deploy` 같은 CLI 명령은 운영 DB 비밀번호나 개인 액세스 토큰이 필요하므로 AI 환경에서 쓰지 않습니다.
- **`service_role` 키(새 이름 secret key)는 AI에게 주지 않습니다**(`agentic.md`). Edge Functions에 필요하면 Supabase의 비밀값으로 등록합니다.
- **되돌릴 지점을 확인합니다.** Pro는 최근 7일의 일일 백업이 있고, 시점 복구(PITR)는 유료 추가 기능입니다. Free는 자동 백업이 없고 기본 `supabase db dump`는 구조만 받습니다. 변경 전에 담당자가 기관 컴퓨터에서 `supabase db dump --data-only -f data.sql`로 데이터를 받아 기관이 정한 보관 위치에 둡니다. 구조는 `supabase/migrations`의 파일로 남아 있습니다. 개인정보가 든 파일이므로 AI 작업 환경에서 만들거나 저장소에 올리지 않습니다. 이 절차가 부담스러우면 Pro의 자동 백업을 씁니다.

## Google Sheets를 보조 도구로 사용하기

Supabase Table Editor에서는 데이터를 조회하고 수정할 수 있지만 Google Sheets처럼 셀 수식을 바로 사용할 수는 없습니다. 반복되는 집계는 데이터베이스 뷰로 만들고, 일회성 분석은 필요한 데이터만 Google Sheets로 가져와 처리합니다.

자주 사용하는 실인원·연인원 집계는 뷰로 정의합니다. 원본이 변경되면 뷰의 조회 결과도 함께 갱신됩니다.

```sql
CREATE VIEW v_실적_연간 AS
SELECT 연도, 프로그램, 성별, 연령대,
       COUNT(DISTINCT 이용자ID) AS 실인원,
       COUNT(*)                 AS 연인원
FROM 참여기록
GROUP BY 연도, 프로그램, 성별, 연령대;
```

일회성 계산에는 GAS로 `현재 데이터 가져오기` 기능을 만들어 필요한 데이터만 시트에 복사할 수 있습니다. 이때 원본은 Supabase이고 시트는 계산과 보고서 작성을 위한 임시 작업 공간입니다. 시트에 개인정보가 포함되면 해당 파일도 보호 대상이므로 공유 권한과 보관 기간을 제한하고 작업이 끝나면 정해진 절차에 따라 삭제합니다.

## 운영 규칙

- Supabase 프로젝트와 Cloudflare 계정은 개인 계정이 아니라 기관이 관리하는 계정으로 생성합니다.
- 후임자가 데이터를 확인할 수 있도록 Supabase Table Editor의 위치와 기본 사용법을 인수인계합니다.
- 개인정보 처리방침과 위탁 문서에 실제 수탁자와 처리 내용을 반영합니다. DPA를 체결했는지는 `../../ops/consent-notes.md`의 확인 항목으로 점검합니다.
