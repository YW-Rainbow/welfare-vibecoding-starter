# 에이전트형 개발·배포의 안전 경계

> 출처·최신판: https://github.com/YW-Rainbow/welfare-vibecoding-starter
> 적용 대상: Claude Code, Codex처럼 프로젝트 파일을 수정하고 명령 실행과 배포까지 수행하는 에이전트형 AI 도구
> 사용자는 개발 지식이 없다고 가정합니다. 전문용어가 처음 나오면 `../glossary.md`의 설명을 참고해 한 문장으로 풀어서 설명하세요.

이 파일은 선택한 플랫폼 문서와 함께 앱 저장소의 `CLAUDE.md` 또는 `AGENTS.md`에 반영합니다. 이 문서는 에이전트의 작업 순서를 지정하지 않습니다. 아래 안전 경계와 완료 조건 안에서 조사, 구현, 도구 선택과 검증 방법은 에이전트가 작업 규모와 위험에 맞게 정합니다.

## 자율적으로 진행할 범위

- 사용자의 목적과 기존 프로젝트에서 작업 범위를 추론하고, 되돌릴 수 있는 조사·구현·수정은 별도 승인 없이 진행합니다.
- 결과를 크게 바꾸는 정보가 빠져 있을 때만 질문합니다. 질문하기 전에는 읽기와 분석 등 이미 허용된 일을 먼저 진행해 사용자가 검토할 수 있는 구체적인 안을 만듭니다.
- 현재 요구를 충족하는 가장 단순한 구조를 선택합니다. 구체적인 순서는 아래 "가장 단순한 구현을 고릅니다"를 따릅니다.
- 아래에 적힌 구현 예시는 목적을 달성하는 한 다른 방법으로 바꿀 수 있습니다. 안전 경계를 다른 방식으로 충족했다면 선택 이유와 검증 결과를 남깁니다.

## 가장 단순한 구현을 고릅니다

코드를 쓰기 전에 다음 순서로 확인하고, 처음 해당하는 항목에서 멈춥니다.

1. 이 기능이 지금 필요한가. 나중에 필요할지 모른다는 기능은 만들지 않고 한 줄로 그렇게 말합니다.
2. 이 프로젝트에 이미 있는가. 같은 일을 하는 함수, 시트, 화면이 있으면 그것을 씁니다.
3. 플랫폼이 기본으로 해 주는가. 구글 시트의 데이터 확인 기능, 데이터베이스의 제약 조건, 브라우저의 날짜 입력창처럼 이미 있는 기능을 코드로 다시 만들지 않습니다.
4. 이미 설치한 것으로 되는가. 몇 줄로 되는 일에 새 라이브러리나 서비스를 추가하지 않습니다.
5. 그래도 필요하면 동작하는 최소한의 코드만 씁니다.

- 요청하지 않은 추상화를 만들지 않습니다. 구현이 하나인 인터페이스, 바뀌지 않는 값을 담은 설정 파일, 나중을 대비해 미리 만드는 빈 코드는 만들지 않습니다.
- 오류는 증상이 아니라 원인을 고칩니다. 고치려는 함수를 부르는 곳을 모두 확인하고, 공통 지점 한 곳에서 고칩니다.
- 단순하게 만들었지만 한계가 있는 부분은 코드 주석에 한계와 다음 단계를 적습니다.

다음은 단순화의 대상이 아닙니다. 사용자와 권한 확인, 삭제 완결성, 접근 로그, 동의 확인, 입력값 검증, 개인정보가 유출되지 않게 하는 처리, 접근성 기준, 인쇄·엑셀 요건, 그리고 사용자가 명시적으로 요청한 기능. 사용자가 전체 구현을 원한다고 하면 다시 설득하지 않고 만듭니다.

이 절은 [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail)(MIT)의 원칙을 사회복지 앱에 맞게 고쳐 쓴 것입니다.

## 운영 데이터를 에이전트에게 제공하지 않습니다

에이전트가 운영 데이터베이스를 조회하거나 실제 이용자 정보가 포함된 파일을 읽으면 그 내용이 AI 서비스 제공자에게 전송될 수 있습니다. 이용자가 앱의 AI 분석 기능에 동의했더라도 개발 도구의 대화 컨텍스트에 개인정보를 제공해도 된다는 뜻은 아닙니다.

- 개발·디버깅·테스트에는 가상 데이터인 **시드 데이터**만 사용합니다. `seed.sql`이나 시드 스크립트를 프로젝트에 포함합니다.
- 운영 데이터베이스의 접속 정보(키, 비밀번호)는 에이전트에게 주지 않습니다. 개발과 테스트는 분리한 개발용 프로젝트나 브랜치 데이터베이스와 개발용 인증 정보로 합니다. 운영 DB를 바꿔야 할 때는 아래 "운영하고 있는 앱에 반영하는 일과 DB를 바꾸는 일은 사람이 결정하고 AI가 실행합니다"의 방식으로만 합니다.
- 운영 장애를 조사할 때는 오류 로그에서 개인정보를 제거하거나 마스킹한 뒤 전달합니다. 가능하면 같은 상황을 시드 데이터로 재현합니다.
- 스크린샷, CSV, 로그 파일을 에이전트에게 제공하기 전에 개인정보가 포함되어 있는지 확인합니다.

## 인증 정보에는 최소 권한을 적용합니다

에이전트가 사용하는 토큰의 권한 범위가 넓을수록 사고가 발생했을 때 영향을 받는 범위도 커집니다.

- 배포 토큰은 해당 프로젝트에 필요한 권한만 포함해 발급합니다. 계정 전체에 접근할 수 있는 토큰은 사용하지 않습니다.
- `service_role` 키와 관리자 키는 에이전트의 환경변수에 넣지 않습니다. RLS를 우회하는 키가 필요하다는 제안이 나오면 먼저 권한 설계를 다시 검토합니다.
- 인증 정보는 `.env`나 비밀값 저장소에서 관리합니다. 키가 코드, 커밋, 로그에 노출되면 즉시 해당 키를 폐기하고 다시 발급합니다. `.gitignore`에 `.env*`와 `.clasprc.json`이 포함되어 있는지 확인합니다.
- 유효기간이 긴 토큰은 쓰지 않으면 정기적으로 폐기합니다. 점검 주기를 기관 캘린더와 인수인계 문서에 기록합니다.

## 위험에 비례해 검증합니다

사람이 모든 코드를 검토하기 어려우므로 배포 전에 중요한 오류를 걸러 낼 수단이 필요합니다. 변경 규모와 데이터 등급에 맞는 테스트, 정적 검사 또는 수동 점검을 선택합니다. 작은 문구 수정에 전체 회귀 테스트를 요구하지 않고, 개인정보의 권한·삭제·로그처럼 실패하면 영향이 큰 기능은 자동 테스트를 우선합니다.

당사자가 직접 사용하는 화면은 `../requirements/design.md`의 배포 전 체크리스트를 함께 적용합니다. 키보드 조작, 포커스 표시, `label`, 색 대비, 200% 확대를 확인합니다. 종이나 엑셀로 출력하는 기록은 `../requirements/print.md`의 한글 글꼴, 페이지별 머리글, 서식 칸 수, 개인정보 열 기본 제외, 출력·반출 기록도 확인합니다.

개인정보를 다루는 앱에서 관련 기능이 있을 때 확인할 항목:

- [ ] RLS·권한: 다른 계정으로 권한이 없는 행을 조회하면 거부되는가
- [ ] 파일 저장소: public URL로 접근하면 거부되고 유효기간이 있는 signed URL만 허용되는가
- [ ] 삭제 완결성: 행을 삭제한 뒤 연결 파일과 파생 데이터가 남지 않는가
- [ ] 접근 로그: 조회·수정·삭제·출력 내역이 기록되고 로그를 임의로 수정하거나 삭제할 수 없는가
- [ ] 비밀값 검사: 빌드 결과와 Git 이력에 API 키나 토큰이 포함되지 않았는가

반복해서 확인해야 하는 항목은 테스트로 만듭니다. AI가 코드를 올리기 전에 AI 작업 환경(Claude Code 클라우드 환경이나 내 컴퓨터)에서 실행하고, 플랫폼의 빌드 명령에도 넣어 테스트가 실패하면 배포가 멈추게 합니다. 플랫폼이 GitHub 저장소와 연결되어 직접 배포한다면 GitHub Actions는 없어도 됩니다. 적용되지 않는 항목은 억지로 구현하지 않고 제외 이유를 기록합니다.

## 되돌리기 어려운 작업은 확인 후 실행합니다

다음 작업은 대상, 영향, 복구 방법을 확인하고 사용자의 명시적인 승인을 받은 뒤 실행합니다. 승인받았고 실행 환경의 권한과 보호 장치가 충분하다면 에이전트가 수행할 수 있습니다. 운영 데이터 전체나 계정 자체를 없애는 작업은 가능하면 사용자가 관리 콘솔에서 직접 실행합니다.

- 운영 데이터베이스의 `DROP`, `TRUNCATE`, 대량 `DELETE`, 운영 마이그레이션 적용
- 버킷·프로젝트 삭제와 도메인·DNS 변경
- 결제 플랜 변경과 토큰·API 키의 발급·폐기

## 운영하고 있는 앱에 반영하는 일과 DB를 바꾸는 일은 사람이 결정하고 AI가 실행합니다

코드를 운영하고 있는 앱(실제 직원과 이용자가 쓰는 앱과 DB)에 반영하는 일과 운영 데이터베이스를 바꾸는 일은 사람이 결정합니다. 에이전트형 도구를 쓴다면 결정한 뒤 실제로 올리고 적용하는 일은 AI가 합니다. 사람이 SQL이나 배포 명령을 콘솔에 직접 입력하면 오타가 생기기 쉽고 무엇을 했는지 기록도 남지 않습니다. 다만 운영 데이터 전체나 계정 자체를 없애는 일은 앞 절("되돌리기 어려운 작업은 확인 후 실행합니다")에 따라 가능하면 사람이 관리 콘솔에서 직접 합니다.

여기서 DB 변경은 테이블·컬럼 구조를 바꾸는 마이그레이션과 여러 행을 한꺼번에 고치거나 지우는 작업입니다. 담당자가 앱 화면, 시트, Table Editor에서 하는 평소의 입력과 수정, `../data/levels.md` 4단계의 기준 행 추가는 해당하지 않습니다.

- **바뀌는 내용을 먼저 보고합니다.** 반영 전에 바뀌는 파일과 달라지는 동작을 보고합니다. DB 변경이라면 영향을 받는 행의 수를 `COUNT`로 세어 보고하고, 행의 내용은 조회하지 않습니다. 사용자가 이 보고를 읽고 실행을 허락하는 것이 사람의 결정입니다.
- **스테이징에서 먼저 확인합니다.** 운영과 분리해 가상 데이터만 넣은 스테이징(테스트용 사이트와 DB)에 먼저 반영하고, 사람이 직접 써 본 뒤 운영하고 있는 앱에 반영합니다. 운영 데이터나 운영 백업을 스테이징에 넣지 않습니다.
- **승인은 규칙 문장이 아니라 설정으로 강제합니다.** 규칙 파일에 "승인 전에는 운영하고 있는 앱에 반영하지 않는다"고 적거나 대화에서 약속하는 것만으로는 부족합니다. AI가 규칙을 놓칠 수 있고, 대화로 정한 약속은 대화가 길어져 요약되는 과정에서 사라질 수 있습니다. 운영하고 있는 앱에 반영하거나 운영 DB를 바꿀 때 쓰는 명령과 커넥터 도구는 `.claude/settings.json`의 확인(`ask`) 규칙에 넣습니다. 확인 규칙은 자동 모드에서도 반드시 묻습니다. 자동 모드에서는 확인 규칙이 없는 커넥터 호출을 사람이 아니라 안전 여부를 판단하는 별도 AI(분류 모델)가 승인하므로, 커넥터 도구도 확인 규칙에 넣습니다.
  - Codex는 `.claude/settings.json`을 읽지 않으므로 같은 명령을 저장소의 `.codex/rules/`에 `prefix_rule(pattern = [...], decision = "prompt")`로 넣습니다. Codex의 규칙은 명령의 앞부분만 비교하므로 `["git", "push"]`, `["npx", "wrangler", "d1"]`, `["clasp", "--project", ".clasp.prod.json"]`처럼 앞에서부터 적습니다.
  - `.codex/rules/`는 명령에만 적용됩니다. 커넥터 도구는 저장소의 `.codex/config.toml`에서 해당 서버에 `default_tools_approval_mode = "prompt"`를 두거나 도구마다 `approval_mode = "prompt"`를 넣습니다.
  - 두 설정은 Codex에서 이 저장소를 신뢰한다고 설정해야 적용됩니다. 규칙 파일은 아직 실험 단계인 기능이므로 문법은 Codex 공식 문서에서 확인합니다.
- **AI에게 보이는 인증 정보로는 개인정보에 바로 닿지 않게 합니다.** 확인 규칙은 AI가 평소 쓰는 형태의 명령을 멈추게 할 뿐 보안 경계는 아닙니다. 그래서 권한 자체를 좁힙니다.
  - OAuth로 연결한 커넥터처럼 AI에게 키가 보이지 않는 방식을 먼저 씁니다. 키가 보이지 않아도 운영에 연결한 커넥터는 조회 도구로 행을 읽을 수 있으므로, 평소에는 스테이징에만 연결하고 운영 연결은 승인한 작업에만 켰다가 끕니다.
  - 인증 정보가 AI에게 보일 수밖에 없다면 배포만 할 수 있는 별도 계정(배포 전용 계정이나 서비스 계정)을 만들어 쓰고, 그 계정에는 데이터 권한을 주지 않습니다.
  - Claude Code 클라우드 환경의 환경변수는 그 환경을 쓰는 모든 사람과 세션이 읽을 수 있습니다. 토큰을 둔다면 그 앱 전용 환경을 따로 만들고 조직 공유 환경에는 넣지 않습니다. Pro·Max 플랜은 환경의 API credentials에 등록하면 AI도, AI가 실행하는 명령도 값을 볼 수 없습니다(Team·Enterprise 플랜에는 아직 없습니다).
  - 앱이 쓰는 비밀값은 GitHub이 아니라 플랫폼의 비밀값 저장소에 둡니다.
- **DB 변경은 파일로 남기고 순서를 지킵니다.** 변경 SQL은 마이그레이션 파일로 저장소에 남기고 스테이징, 운영 순서로 적용합니다. 컬럼을 추가할 때는 DB를 먼저 바꾸고 코드를 올립니다. 컬럼을 지울 때는 그 컬럼을 쓰지 않는 코드를 먼저 올린 뒤 DB에서 지웁니다. 이름을 바꿀 때는 새 컬럼 추가, 새 컬럼을 쓰는 코드 반영, 옛 컬럼 삭제의 세 단계로 나눕니다.
  - 보관 등급 2 이상 테이블, 증거급 기록, 접근 로그에서는 컬럼을 지우거나 이름을 바꾸지 않습니다. 새 컬럼을 더하고 옛 컬럼은 보존 기간이 끝난 뒤 파기 절차로 지웁니다(`../data/record-integrity.md`).
  - 여러 앱이 같은 명부 DB를 쓰면 그 DB의 마이그레이션은 명부를 관리하는 저장소 한 곳에서만 만들고 적용합니다. 컬럼을 지우거나 이름을 바꾸기 전에는 그 DB를 쓰는 모든 앱의 코드를 먼저 바꿉니다.
- **되돌릴 지점을 먼저 확인합니다.** 반영 전에 이전 배포 버전과 DB의 복구 지점(시점 복구나 백업)을 확인해 보고에 적습니다. DB를 과거 시점으로 되돌리면 그 뒤에 들어온 기록과 접근 로그가 사라지고, 그 뒤에 파기한 기록은 되살아납니다. 그래서 복구는 마지막 수단입니다. 먼저 변경을 되돌리는 마이그레이션으로 해결할 수 있는지 검토합니다. 그래도 복구해야 한다면 사람이 복구 지점 이후의 접근 로그를 미리 내보내 둡니다. 복구한 뒤에는 `../../ops/destruction-log.md`에서 복구 지점 이후에 파기한 항목을 다시 파기합니다.

확인 규칙은 AI가 운영하고 있는 앱에 처음 반영할 준비를 할 때 선택한 플랫폼에 맞게 고쳐 저장소의 `.claude/settings.json`에 넣고 커밋합니다. 어떤 명령에서 승인을 묻게 되는지 사용자에게 설명합니다. 커밋해 두면 후임자와 다른 세션도 같은 확인을 거칩니다. 예시는 다음과 같습니다.

```json
{
  "permissions": {
    "ask": [
      "Bash(*git push*main*)",
      "Bash(*gh pr merge*)",
      "mcp__*__merge_pull_request",
      "mcp__*__enable_pr_auto_merge",
      "mcp__*__push_files",
      "mcp__*__create_or_update_file",
      "mcp__*__delete_file",
      "Bash(*wrangler d1 execute* --remote*)",
      "Bash(*wrangler d1 migrations apply* --remote*)",
      "Bash(*wrangler d1 time-travel restore*)",
      "mcp__*__d1_database_query",
      "mcp__*__r2_bucket_delete",
      "Bash(*wrangler r2 bucket delete*)",
      "mcp__*__execute_sql",
      "mcp__*__apply_migration",
      "mcp__*__deploy_edge_function",
      "Bash(*firebase*deploy*)",
      "Bash(*gcloud run deploy*)",
      "Bash(*gcloud run jobs*)",
      "Bash(*gcloud functions deploy*)",
      "Bash(*gcloud functions call*)",
      "Bash(*.clasp.prod.json*)",
      "Bash(*clasp deploy*)",
      "Bash(*clasp*-deployment*)",
      "Edit(**/.clasp.json)",
      "Edit(./.claude/settings.json)"
    ],
    "deny": [
      "mcp__*__d1_database_delete",
      "mcp__*__kv_namespace_delete",
      "Bash(*wrangler d1 delete*)",
      "Bash(*wrangler kv*namespace delete*)"
    ]
  }
}
```

- 커넥터 도구의 이름은 연결한 방식(클라우드 환경, 터미널, 데스크톱 앱)에 따라 다를 수 있으므로 서버 이름 자리에 `*`를 씁니다. 이름이 틀려도 경고가 나오지 않으므로 처음 한 번은 AI에게 실제 도구 이름을 확인하게 합니다. 서버 이름 자리에 `*`를 쓰면 스테이징에 연결한 도구도 승인을 묻게 되지만 그대로 둡니다.
- GitHub 도구로 main에 바로 파일을 쓰거나 자동 합치기(auto-merge)를 켜는 것도 운영하고 있는 앱에 반영하는 일이므로 함께 넣습니다.
- 데이터베이스를 통째로 지우는 도구와 명령은 앞 절에 따라 사람이 관리 콘솔에서 하므로 `ask`가 아니라 `deny`(금지)에 넣습니다. 스테이징 데이터베이스를 지울 때도 콘솔에서 합니다.
- Supabase CLI의 `supabase db push`, `supabase db dump`, `supabase functions deploy`는 운영 DB 비밀번호나 개인 액세스 토큰이 있어야 하므로 AI 작업 환경에서 쓰지 않습니다.
- 채팅에서 코드를 받아 직접 붙여 넣는 방식이라면 AI가 실행할 수 없으므로 사람이 올립니다. 스테이징에서 먼저 확인하고 되돌릴 지점을 적어 두는 것은 똑같이 합니다.

플랫폼별 방법은 선택한 `rules/` 파일에 있습니다. 경로 B와 A'-Azure처럼 전용 규칙 파일이 없으면 이 절의 기준을 그 플랫폼에 맞게 직접 적용합니다.

## 변경 이력과 인수인계 절차를 저장소에 남깁니다

에이전트와 나눈 대화는 인수인계 자료가 될 수 없습니다. 후임자가 작업을 이어갈 수 있도록 코드, 규칙, 실행 절차를 저장소에 기록합니다.

- 소스와 설정은 Git으로 관리합니다. 사용자가 커밋을 요청했거나 기존 작업 흐름에 커밋이 포함되어 있다면 무엇을 왜 바꿨는지 알 수 있는 메시지를 사용합니다.
- 프로젝트의 `CLAUDE.md`나 `AGENTS.md`에 이 파일과 선택한 플랫폼 규칙을 포함합니다. 후임자가 같은 규칙을 읽고 작업을 재개할 수 있어야 합니다.
- `../../ops/handover.md`에는 사용한 AI 도구, 규칙 파일, 실행 명령, 스테이징 주소, AI에게 준 권한과 인증 정보의 보관 위치를 기록합니다. 인증 정보 자체는 문서에 적지 않습니다.

## 사용자와 에이전트의 결정 범위를 구분합니다

사용자는 단순한 승인자가 아니라 앱의 목적과 범위를 정하는 사람입니다. 에이전트는 구현 방법을 제안하고 위험과 대안을 설명하지만, 기관의 정책 결정을 대신하지 않습니다.

다음 사항은 사용자가 결정합니다.

- 앱을 만드는 목적과 포함하거나 제외할 업무
- 기획 확정, 운영하고 있는 앱에 반영할지와 운영 DB를 바꿀지
- 앱을 만들지 않거나 기존 절차를 폐지하는 결정

사용자의 목적, 현장에 관한 설명과 명시적인 결정은 일반적인 개발 권장사항보다 우선합니다. 개인정보 보호, 법적 의무, 보안 또는 되돌리기 어려운 영향과 충돌할 때만 구체적인 근거와 대안을 설명하고 확인합니다. 단순한 기술 취향을 이유로 사용자의 결정을 뒤집지 않습니다.

요청을 그대로 구현할 수 없다면 고정된 형식을 채우기보다 이유, 요청의 목적, 같은 목적을 달성할 대안을 간결하게 설명합니다.

다음 요청은 사용자 지시가 있어도 위험을 확인하지 않은 채 실행하지 않습니다. 구체적인 위험과 더 안전한 대안을 설명하고 사용자가 결정하게 합니다.

- RLS나 서버의 권한 검사를 끄는 작업
- `service_role` 키나 관리자 키를 프론트엔드 코드 또는 에이전트 환경에 넣는 작업
- 실제 이용자의 데이터를 에이전트 대화에 제공하는 작업
- 스테이징 확인과 승인 없이 운영 데이터베이스에 마이그레이션이나 대량 삭제를 적용하는 작업
- 접근 로그를 삭제하거나 기록 기능을 끄는 작업
- 지문·얼굴 같은 생체인식정보를 수집하는 기능을 `../assess/ethics.md`의 검토 없이 만드는 작업

새로운 외부 서비스 연동, 되돌리기 어려운 데이터 구조 변경, 예상하지 못한 비용, 개인정보 항목 추가·변경이 기존 요청에서 승인되지 않았다면 영향과 선택지를 설명하고 확인을 받습니다. 이미 사용자가 선택했거나 요구사항에 포함된 사항은 반복해서 승인받지 않습니다.
