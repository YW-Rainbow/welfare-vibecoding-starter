# Google Apps Script + Google Sheets 개발 기준(경로 C)

> 출처·최신판: https://github.com/YW-Rainbow/welfare-vibecoding-starter
> 적용 대상: Google Workspace 조직 내부에서 사용하는 P등급 이하의 소규모 앱, 그리고 아래 "S등급을 시트에 둘 때의 조건"을 모두 갖춘 소량 S등급 앱(사례관리 등)
> 기준일: 2026-09
> 이 문서는 `agentic.md`와 함께 적용합니다.

이 문서의 보안·권한·파기 요건은 반드시 지킵니다. 나머지 설정과 구현 예시는 소규모 기관을 위한 기본값이며, 같은 결과를 더 단순하게 달성할 수 있다면 이유와 검증 방법을 남기고 바꿀 수 있습니다.

## 지켜야 할 조건

### 권장 배포 설정

- 사용자마다 볼 열이나 행이 다르거나(예: 강사에게 연락처를 숨김) 시트를 공유하지 않으려면 실행 사용자를 **나**(스크립트를 소유한 기관 계정. S등급이면 앱 전용 계정), 액세스 권한을 **조직 내 사용자**로 둡니다. clasp로 배포한다면 아래 "배포" 절 2·3번의 **나** 조건을 따릅니다.
- 실행 사용자를 **웹 앱에 액세스하는 사용자**로 두면 사용자에게 시트 권한이 있어야 동작하고, 권한이 있는 사용자는 시트를 직접 열어 앱의 권한 검사를 건너뛸 수 있습니다. 모든 사용자가 시트 전체를 봐도 되는 앱에만 씁니다.
- 개인정보를 다루는 앱에서 `실행 사용자: 나`와 `액세스 권한: 모든 사용자`를 함께 사용하지 않습니다. 이렇게 설정하면 로그인하지 않은 방문자도 개발자 계정의 권한으로 스크립트를 실행할 수 있습니다.

### 모든 조회·수정 함수에서 사용자와 권한 확인

```javascript
function doGet(e) {
  const email = Session.getActiveUser().getEmail();
  if (!email) return unauthorized_();          // 사용자 인증
  if (!canAccess_(email, e.parameter.id)) {    // 이 사용자가 해당 행에 접근할 권한이 있는지 확인
    return forbidden_();
  }
  // 이후 로직
}
```

로그인했다고 데이터를 볼 권한이 있는 것은 아닙니다. `e.parameter.id`를 그대로 사용해 행을 반환하면 IDOR 취약점이 생기므로 각 요청에서 그 행에 접근할 권한이 있는지 확인합니다.

### 데이터 시트 관리

- 데이터 시트는 앱 전용 폴더에 두고 다른 사용자에게 직접 공유하지 않습니다(실행 사용자가 **웹 앱에 액세스하는 사용자**인 앱은 예외이며, 위 "권장 배포 설정"의 조건을 따릅니다). 조회와 수정은 앱에서만 허용합니다. 시트 링크를 공유해야 한다는 요구가 있으면 필요한 항목만 보여 주는 읽기 전용 화면을 만듭니다.
- 구글 시트에 두면 데이터가 국외에 보관됩니다. 개인정보 처리방침의 국외 처리위탁 목록에 Google을 올립니다(제28조의8 제1항 제3호). 이용 계약이 있는 이용자(무료 프로그램 신청자도 포함합니다)와 직원은 이것으로 되고 동의는 필요 없습니다. 설문 응답자나 신청 없이 참여한 행사 참가자처럼 계약이 없는 사람의 정보를 폼과 시트로 받는다면 수집 양식에 국외이전 동의 항목을 둡니다(`../../ops/consent-notes.md` 1절). 앱을 만들 때 기관의 처리방침에 이 항목이 있는지 확인하고 없으면 추가하라고 안내합니다.
- Google Sheets는 데이터베이스가 아닙니다. 연간 수만 행 이상이 예상되거나 여러 사용자가 자주 동시에 저장한다면 `../workflow.md`의 경로 A나 F를 검토합니다.

### S등급을 시트에 둘 때의 조건

사례관리처럼 민감정보가 든 소량 기록을 시트에 두려면 아래를 모두 갖춥니다. 시트를 공유해서 함께 쓰는 앱과 시트가 뒤에 숨은 앱은 전혀 다릅니다. 이 조건들은 `agentic.md`의 "단순화의 대상이 아닙니다" 목록에 해당하므로 요청이 없어도 빼지 않습니다.

- **소유**: 데이터 시트, 로그 시트, 첨부 폴더는 이 앱만을 위해 만든 기관 앱 계정이 소유합니다. 이 계정에는 다른 파일을 두지 않고 2단계 인증을 켭니다. 시트와 폴더는 어떤 사람에게도 공유하지 않고, 편집 권한은 기관 관리자 계정 하나에만 둡니다.
- **배포**: 실행 사용자를 **나**(앱 계정), 액세스 권한을 **조직 내 사용자**로 설정해 배포합니다. 시트를 공유하지 않으면서 담당자가 웹앱을 쓰게 하는 조합은 이것뿐입니다. 금지된 조합은 "나 + 모든 사용자"입니다. 같은 Workspace 도메인이면 `Session.getActiveUser().getEmail()`로 접속한 담당자를 알 수 있습니다.
- **권한**: 담당자와 이용자의 배정표를 시트에 두고, 모든 조회·수정 함수는 접속한 담당자가 그 이용자의 담당인지 확인한 뒤 행을 반환합니다. 관리자 역할도 배정표에 명시합니다.
- **로그**: 조회, 수정, 출력, 첨부 열기를 모두 로그 시트에 남기고 2년 보관합니다. 월 1회 데이터 시트와 로그 시트를 CSV로 내보내 날짜별 폴더에 저장하고, 행 수와 SHA-256 해시를 기관 관리자가 볼 수 없는 메일(Workspace 밖의 기관 명의 계정 등, `../data/record-integrity.md`의 "외부 검증 정보의 보관 위치")로 보냅니다. CSV 자체는 보내지 않습니다(`../data/record-integrity.md` 보관 등급 2~4를 매일이 아니라 월 1회로 줄인 방식). 편집 권한이 있는 관리자가 시트를 고치는 것은 막을 수 없고 이 해시로 사후에 확인합니다.
- **항목**: 주민등록번호는 저장하지 않습니다. 이용자는 명부의 ID로 참조하고, 자유서술 칸에도 이름 대신 ID를 쓰도록 화면에서 안내합니다.
- **첨부**: 사진과 문서는 앱 계정의 비공개 폴더에 두고, 웹앱이 권한을 확인한 뒤 열거나 다운로드하게 합니다. 파일 링크를 화면에 직접 노출하지 않습니다.
- **범위**: 대량이거나 기관의 핵심 시스템이면 이 조건으로도 부족합니다. `../workflow.md`에서 S등급이 대량이거나 핵심 시스템인 경우의 안내에 따라 기성 제품을 검토합니다.
- **희망이음**: 기록은 이 앱에 처음 작성하고, 희망이음에는 법에 따라 제출할 내용을 입력합니다. 그래서 이중 입력은 남습니다. 희망이음 입력 항목 순서대로 복사할 수 있는 화면을 두면 옮겨 적는 시간을 줄일 수 있습니다.

### 접근 로그

- 별도 로그 시트에 개인정보를 조회·수정·삭제·출력할 때마다 `[접속 일시, 계정, 수행 업무, 대상 행 ID]`를 기록합니다. GAS 웹앱에서는 접속지 IP를 안정적으로 확보할 수 없으므로 이 한계를 내부관리계획에 기록합니다.
- 민감정보 처리 시스템의 접속기록은 적용되는 법적 기준에 따라 필요한 기간 동안 보관합니다. 개인정보 원본을 파기하더라도 접속기록의 보관 기간이 끝나지 않았다면 로그를 삭제하지 않습니다.
- 로그 시트도 직접 공유하지 않습니다. 이상 조회가 있는지 확인하는 정기 점검 일정을 기관 캘린더에 등록합니다.

### HTML 출력과 XSS 방지

사용자 입력값을 문자열로 연결해 HTML을 만들지 않습니다. `HtmlService.createTemplate`을 사용하고 출력값을 이스케이프 처리합니다.

### 인쇄·PDF·엑셀의 권장 기본값

자세한 기준은 `../requirements/print.md`를 참고합니다.

- 웹앱 화면은 `window.print()`와 `@media print`를 사용해 브라우저에서 인쇄합니다. 이 방식은 사용자의 컴퓨터에 설치된 한글 글꼴을 사용하므로 PDF 라이브러리의 글꼴 호환 문제를 줄일 수 있습니다.
- 기관 서식은 별도의 출력용 시트를 만들고 `getAs(MimeType.PDF)` 또는 내보내기 URL로 PDF를 생성합니다. 용지, 여백, 출력 범위를 명시하고 업무용 데이터 시트를 그대로 출력하지 않습니다.
- 여러 건을 PDF 한 파일로 합쳐야 한다면 처음부터 구현 방법을 결정합니다. `pdf-lib`를 스크립트 파일로 포함해 건별 PDF를 합치거나, 출력용 시트에 여러 건을 배치해 한 번에 내보낼 수 있습니다. 문서별 페이지 구분이 중요하면 전자를 사용합니다.
- 엑셀 내보내기는 필요한 열만 담은 전용 시트로 제공합니다. 개인정보 열이 포함된 원본 시트 전체를 다운로드하게 하지 않습니다.
- 엑셀 가져오기는 원본을 별도 시트에 보존한 뒤 Apps Script로 항목과 값을 검증해 명부에 반영합니다. 기존 값과 새 값의 대응표를 남기는 방법은 `../data/ssot.md`를 참고합니다.

### 삭제 완결성

- 행을 삭제할 때 연결된 Google Drive 파일도 함께 삭제합니다. 즉시 삭제하기 어렵다면 삭제 대기 폴더로 옮기고 정해진 일정에 일괄 파기합니다.
- `retention_until` 열에 보관 만료일을 기록하고 시간 기반 트리거로 만기 데이터를 파기합니다.
- 파기 결과는 별도의 파기 대장 시트에 기록합니다.

## 동시 사용자가 늘어날 때 검토할 방법

여러 사용자가 동시에 저장하면서 지연이나 충돌이 발생하면 실제 병목을 측정한 뒤 아래 방법 가운데 필요한 것을 선택합니다. 번호는 적용 순서를 뜻하지 않습니다.

### 1. LockService 적용 구간을 줄인다

읽기와 계산은 lock을 획득하기 전에 처리하고, lock 안에서는 쓰기만 수행합니다.

```javascript
const data = sheet.getDataRange().getValues();   // lock 밖에서 읽기
const newRow = compute(data);                     // lock 밖에서 계산
lock.waitLock(30000);
sheet.appendRow(newRow);                          // lock 안에서는 쓰기만 수행
lock.releaseLock();
```

### 2. 사용자별 입력 시트를 분리한다

직원별 스프레드시트에 입력하고 시간 기반 트리거로 마스터 시트에 통합합니다. 같은 파일에 동시에 쓰는 충돌을 줄일 수 있지만, 통합 트리거가 실패하면 집계에서 기록이 누락될 수 있으므로 실패 알림과 재처리 절차가 필요합니다.

### 3. 입력용 시트와 조회용 시트를 분리한다

입력용 시트에는 새 행을 추가하기만 하고, 트리거가 조회용 시트를 갱신하게 합니다. 입력과 복잡한 조회가 같은 시트에서 겹치는 시간을 줄일 수 있습니다.

### 4. 단순한 입력은 Google Forms로 전환한다

신청 접수, 출결, 만족도처럼 정형화된 입력은 Google Forms가 적합할 수 있습니다. 기존 도구로 요구사항을 충족할 수 있다면 별도의 앱을 만들 필요가 없습니다.

다음 방식은 사용하지 않습니다.

- CacheService에 입력값을 임시로 모은 뒤 시트에 저장하는 방식: 캐시는 영구 저장소가 아니므로 기록이 유실될 수 있습니다.
- 연도별로 시트를 분리하는 방식: 스크립트 lock 경합을 해결하지 못하고 여러 해의 데이터를 분석하기 어렵게 만듭니다.

위 조치를 적용해도 성능과 운영 문제가 계속되면 Google Sheets를 데이터베이스로 사용하는 구조를 중단하고 `../workflow.md`에서 경로 A를 다시 검토합니다.

## clasp와 Git 사용

브라우저의 Apps Script 편집기에 코드를 붙여 넣는 방식은 설치가 필요 없어 소규모 작업을 시작하기 쉽습니다. Claude Code나 Codex 같은 에이전트형 도구는 로컬 프로젝트 파일이 필요하므로 처음부터 clasp와 Git을 사용합니다. 채팅에서 코드를 받아 직접 붙여 넣는 방식이라도 다음 조건이 생기면 clasp로 전환합니다.

- 파일 수가 늘어 복사와 붙여넣기 과정에서 실수가 발생하기 시작한 경우
- 로컬 파일을 직접 수정하는 에이전트형 AI 도구를 사용하려는 경우
- 코드의 백업, 변경 이력, 인수인계가 필요한 경우

clasp로 전환할 때는 다음 규칙을 적용합니다.

1. 스크립트 프로젝트의 소유자는 개인이 아니라 기관 계정입니다(S등급이면 위의 앱 계정). 스크립트는 데이터 시트의 확장 프로그램 > Apps Script 메뉴에서 만들지 않고 독립 스크립트로 만듭니다. 시트에서 만든 스크립트는 시트와 공유 목록이 같아 스크립트만 따로 공유할 수 없습니다. 운영 스크립트는 소유자 계정으로 script.google.com에서 새 프로젝트로 만들고, 스테이징 스크립트는 AI가 아래 배포 전용 계정으로 `clasp create --type standalone`을 실행해 만들어도 됩니다. 시트는 스크립트 속성에 둔 ID로 `SpreadsheetApp.openById()`를 써서 엽니다. AI가 쓰는 `clasp login`은 배포에만 쓰는 기관 계정으로 따로 합니다. 이 계정에는 스크립트 프로젝트만 편집자 권한으로 공유하고, 데이터 시트와 폴더는 공유하지 않습니다. 배포 전용 계정은 Workspace 관리자가 만들며, 유료 Workspace라면 계정 요금이 하나 더 듭니다. 로그인 인증 정보가 있는 `.clasprc.json`은 저장소에 커밋하지 않습니다.
2. 저장소는 private으로 설정합니다. 코드에 포함될 수 있는 시트 ID와 폴더 ID도 외부에 노출하지 않습니다.
3. 로컬 파일과 Git을 코드의 원본으로 정하고 브라우저 편집기에서 직접 수정하지 않습니다. 긴급 수정도 AI에게 고치게 하고 확인 규칙을 거쳐 운영에 올립니다. 브라우저에서 이미 고쳤다면 `clasp --project .clasp.prod.json pull`로 운영 코드를 받아 커밋합니다. 기본 `.clasp.json`은 스테이징을 가리키므로(아래 "배포" 절) 그냥 `clasp pull`을 하면 운영의 수정 내용을 받지 못합니다.
4. `clasp push` 전에 Git 커밋을 만들어 배포 내용과 코드 이력을 맞춥니다.
5. `../../ops/handover.md`의 소스 코드 위치에 저장소 주소와 `clasp clone <scriptId>` 절차를 기록합니다.
6. clasp 설정과 에이전트 규칙이 갖춰진 템플릿(https://github.com/YW-Rainbow/apps-script-vibe-starter)의 내용을 앱 저장소의 `app/`에 복사해 시작할 수 있습니다. 별도 저장소로 클론해 두 저장소를 운영하지 않습니다. 템플릿 안내의 `clasp login`은 자기 계정이 아니라 위 1번의 배포 전용 계정으로 하고, 템플릿의 `.clasp.json`에는 스테이징 스크립트 ID를 넣습니다. 템플릿의 배포 안내보다 아래 "배포" 절이 우선합니다.

### 배포: 사람이 결정하고 AI가 올립니다

GAS는 GitHub 저장소와 연결해 자동으로 배포하는 기능이 없으므로 AI가 clasp로 직접 올립니다. 원칙은 `agentic.md`의 "운영 반영과 DB 변경은 사람이 결정하고 AI가 실행합니다"를 따릅니다.

1. **배포 전용 계정**: AI가 쓰는 clasp 인증 정보(`.clasprc.json`)는 클라우드 환경이든 내 컴퓨터든 AI가 읽을 수 있는 곳에 있습니다. 그래서 위 1번처럼 데이터에 권한이 없는 배포 전용 계정으로 로그인합니다. clasp의 서비스 계정 지원은 아직 실험 단계라 쓰지 않습니다.
2. **운영 배포의 실행 계정**: 운영 배포(배포 ID)는 처음 한 번 스크립트 소유자 계정으로 만들고, 그 뒤에는 배포 전용 계정이 같은 배포를 새 버전으로 바꿉니다. 실행 사용자를 **나**로 둔 웹앱(위 "S등급을 시트에 둘 때의 조건")은 소유자 권한으로 실행되어야 합니다. 배포 전용 계정으로 처음 새 버전을 올린 뒤 웹앱이 여전히 소유자 권한으로 실행되는지 확인합니다. 소유자 권한으로 실행되지 않으면 배포 전용 계정에 데이터를 공유해서 해결하지 말고, AI는 `clasp push`와 새 버전 만들기까지만 하며 운영 배포를 새 버전으로 바꾸는 일은 사람이 소유자 계정으로 Apps Script 편집기의 배포 관리에서 합니다. 실행 사용자가 **웹 앱에 액세스하는 사용자**라면 접속한 담당자의 권한으로 실행되므로 이 확인은 필요 없습니다.
3. **스테이징**: 가상 데이터 시트의 ID를 스크립트 속성에 넣은 스테이징용 독립 스크립트를 따로 만듭니다. 스테이징 스크립트와 가상 데이터 시트는 운영 데이터에 권한이 없는 계정(배포 전용 계정 등)이 소유합니다. 운영 데이터를 가진 앱 계정이 스테이징을 소유하면 AI가 승인 없이 올린 코드가 그 계정 권한으로 운영 시트에 닿습니다. 기본 `.clasp.json`은 스테이징을 가리키게 하고, AI는 여기에 자유롭게 올립니다. 테스트 주소(`/dev`)는 편집자만 열 수 있습니다. 실행 사용자를 **나**로 둔 앱은 담당자를 스테이징 스크립트의 편집자로 넣어 직접 확인합니다. 실행 사용자가 **웹 앱에 액세스하는 사용자**인 앱은 스테이징도 여는 사람의 권한으로 실행되므로, 담당자 계정으로 열면 AI가 승인 없이 올린 코드가 담당자가 볼 수 있는 운영 시트에 닿습니다. 이런 앱은 운영 시트에 권한이 없는 계정(배포 전용 계정 등)으로 로그인해 확인합니다.
4. **운영**: 운영 스크립트는 `.clasp.prod.json`에 적고 `--project .clasp.prod.json`으로만 다룹니다. 사람이 승인하면 AI가 `clasp --project .clasp.prod.json push`와 `clasp --project .clasp.prod.json update-deployment <운영 배포 ID>`로 운영 배포를 새 버전으로 바꿉니다. 2번의 확인에서 소유자 권한이 유지되지 않았다면 AI는 `push`와 새 버전 만들기까지만 합니다. 확인 규칙은 `Bash(*.clasp.prod.json*)`처럼 운영 파일 이름이 들어간 모든 명령에 걸고, 기본 `.clasp.json`의 대상을 바꾸지 못하게 `Edit(**/.clasp.json)`도 넣습니다(`app/` 아래 어느 폴더에 있어도 걸리게 합니다)(`agentic.md`).
5. **되돌리기**: 웹앱은 배포를 이전 버전으로 되돌립니다(`clasp --project .clasp.prod.json update-deployment <배포 ID> -V <버전>`). 2번의 확인에서 소유자 권한이 유지되지 않았다면 사람이 소유자 계정으로 배포 관리에서 이전 버전을 고릅니다. 설치형 트리거는 만들 때 실행할 배포를 Head(기본값)로 두면 배포 버전이 아니라 마지막으로 올린 코드로 실행되므로, 운영에 `clasp push`만 해도 트리거의 동작이 바뀌고 배포 버전을 되돌려도 트리거는 그대로입니다. 트리거가 어느 배포로 실행되는지 `../../ops/handover.md`에 적습니다. 트리거까지 되돌리려면 이전 커밋의 코드를 다시 올립니다. 데이터는 시트의 버전 기록으로 되돌리며, 파일 전체가 돌아가므로 로그 시트는 데이터 시트와 다른 파일에 둡니다.
6. **시트 구조 변경**: 배포 전용 계정은 데이터 시트에 권한이 없어 AI가 운영 시트의 열을 직접 바꾸거나 행 수를 셀 수 없습니다. 그래서 열 추가와 이름 변경은 AI가 스크립트의 이관 함수(예: `migrate_v2_()`)로 만들어 저장소에 남깁니다. 이 함수에는 시트를 바꾸지 않고 영향받는 행 수만 세어 실행 로그에 보여 주는 세기 모드를 둡니다. 스테이징에서 확인한 뒤 운영에 올리면, 사람이 소유자 계정으로 편집기에서 세기 모드를 먼저 실행해 행 수를 확인하고 적용 모드를 한 번 실행합니다. 적용 전에 시트의 버전 기록에 이름을 붙여 되돌릴 지점을 남깁니다. 보관 등급 2 이상 시트와 로그 시트는 열 이름을 바꾸거나 지우지 않고 새 열을 더합니다(`agentic.md`).
7. **남는 위험**: 스크립트를 고칠 수 있는 계정은 코드를 바꿔 데이터에 닿을 수 있습니다. 실행 사용자가 **나**이면 소유자 계정의 데이터에, **웹 앱에 액세스하는 사용자**이면 접속한 사람이 볼 수 있는 데이터에 닿습니다. 운영 스크립트에 올리는 순간이 곧 데이터에 닿는 순간이므로, 승인 전에 AI가 바뀐 파일과 동작을 보고하게 합니다.

## 운영상 제약

- GAS는 Google Workspace 계정 인증을 활용할 수 있고 Google Sheets를 관리 화면으로 사용할 수 있어 소규모 조직이 도입하고 인수인계하기 쉽습니다.
- Google Sheets의 쓰기 작업은 한 번에 하나씩 순서대로 처리되므로 동시 입력이 많으면 lock 경합이 발생합니다. Apps Script에는 실행 시간 제한과 콜드 스타트도 있습니다.
- 매년 새 시트를 만들면 장기 분석과 이용자별 이력 조회가 어려워집니다. 이 요구가 중요해지면 경로 A로 이전할 시점입니다.
